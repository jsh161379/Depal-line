## 1. 정한 것 (제안서에서 바꾼 점 포함)

| 항목 | 제안 | 정한 내용 | 이유 |
|---|---|---|---|
| 넣을 테이블 | 고객 테이블, 비회원 주문 테이블 | **`orders`** | 지금 DB에는 고객·회원 테이블이 따로 없고, 고객 정보는 주문마다 `orders`에 들어감. 회원 정보를 홈페이지가 따로 저장한다면 그쪽은 홈페이지에서 같은 값으로 맞추면 됨 |
| `customer_type` | VARCHAR(10) | `enum('personal','company')`, 기본 `personal` | 다른 코드 칸(`order_status` 등)과 같이 enum으로 잘못된 값을 막음. 값은 제안 그대로 |
| `age_group` | VARCHAR(10) | `enum('10s','20s','30s','40s','50s+','none')`, 기본 `none` | 위와 같음. 값은 제안 그대로 |
| `region` | VARCHAR(10) | `varchar(10) NOT NULL DEFAULT 'none'` | 시·도 17개 짧은 이름(`서울`, `경기`, `충북` …), 모르면 `none` (주문 관리 반영 제안에 맞춤) |
| 기업 고객의 연령대 | 화면에서 숨김 | 기업이면 연령대가 와도 **`none`으로 저장** | 통계에 기업이 연령대로 섞이지 않게 |
| 지역 자동 입력 | (서버 확인 사항) | 메시지에 지역이 없거나 17개 이름이 아니면 **배송 주소 앞부분으로 채움** | `서울특별시 …`, `경기도 …`, `충청북도 …` 모두 인식. 주소에 시·도가 없으면(예: `수원시 …`) `none` |
| 기존 데이터 | 기본값으로 채움 | 유형 `personal`, 연령대 `none`, **지역은 배송 주소로 채움** | 기존 주문도 지역 통계에 들어가게 |

생년월일을 받지 않고 연령대만 받는 방식은 그대로입니다.

## 2. 메시지 형식 (`order/accepted`에 칸 3개 추가)

```json
{"no":"BR-20261120-7K3Q","ts":"2026-11-20 10:30:00.000","name":"홍길동","phone":"010-1234-5678",
 "addr":"서울 …","memo":"","items":[…],"total":17800,"accepted_at":"2026-11-20 10:30:00.400",
 "customer_type":"personal","age_group":"30s","region":"서울"}
```

| 필드 | 값 | 생략하면 |
|---|---|---|
| `customer_type` | `personal` / `company` | `personal` |
| `age_group` | `10s` / `20s` / `30s` / `40s` / `50s+` / `none` | `none` |
| `region` | 서울, 부산, 대구, 인천, 광주, 대전, 울산, 세종, 경기, 강원, 충북, 충남, 전북, 전남, 경북, 경남, 제주, 또는 `none`(선택 안 함) | 생략·`none`이면 배송 주소에서 뽑음 |

- 세 칸 모두 선택 항목이라 **값이 없거나 틀려도 주문은 거절하지 않고 기본값**(`personal` / `none` / 주소에서 뽑은 지역, 없으면 `none`)으로 저장합니다. 틀린 값이 오면 경고 로그만 남깁니다.
- `order/new`(홈페이지 → 주문 관리)에도 같은 이름으로 넣고, 주문 관리 프로그램이 `order/accepted`에 그대로 실어 주면 됩니다 — **조시현 확인 필요**.
- 칸 3개가 없는 예전 메시지도 그대로 저장됩니다.

## 3. 통계 쿼리 (`주문관리_조회쿼리.sql` `[통계]`, 모두 취소 제외)

## 4. 통계 탭(F4)에 붙일 때 (장성찬)

- `StatsDbReader`가 `orders`에서 `customer_type`, `age_group`, `region`을 같이 읽고, 막대 그래프 2개(연령대별, 지역별)와 순위 표를 추가합니다.
- 주문 모델 `Order`는 Core(공통) 파일이라, 고치려면 `[공통]` PR이 필요합니다. Core를 건드리지 않으려면 통계 탭 안에서 주문번호 → 고객 정보 표를 따로 들고 계산합니다.
- DB에 아직 칸이 없거나 가짜 주문 모드면 "고객 정보 없음"으로 보여 줍니다.

## 5. 적용 순서

1. **서버 PC**: `DB_변경_2026-11-20_고객정보.sql` 실행. 칸이 이미 있으면 건너뛰므로 다시 실행해도 됩니다. 기존 주문의 지역은 배송 주소로 채워지고, 가짜 주문에는 고객 정보가 들어갑니다.
   **새로 만드는 PC**: `teamproject.sql`로 생성
2. `mqtt_db_writer.py`를 바꾸고 다시 실행. DB에 칸이 없으면 시작할 때 `orders has no customer_type/age_group/region` 경고를 남기고 고객 정보만 빼고 저장합니다.
3. 권한은 추가할 것 없음 (`ui_reader`는 이미 `orders`를 읽을 수 있음)

## 6. 검증

- SQLite로 같은 테이블 구조를 만들어 저장 프로그램 시험 42가지 통과 (고객 정보 7가지 추가: 값 저장, 예전 메시지 기본값·주소로 지역, 기업은 연령대 none, 시·도 이름·주소 인식 11가지, 모르는 지역은 주소로, 틀린 값은 기본값으로, 칸이 없는 DB)
- 서버 PC 상황(칸 없는 `orders` + 가짜 데이터)에서 지역 채우기 SQL을 실행해 확인: 26건 중 25건 채움, 시·도 없는 `수원시 …` 1건만 `none`
- 새 PC(`teamproject.sql`)와 서버 PC 두 경우 모두 가짜 데이터를 두 번 넣어 확인, 외래 키 오류 없음
- 새 통계 쿼리 5개를 가짜 데이터로 실행해 확인
- **실제 MySQL 8.2에서는 아직 실행해 보지 않았습니다.** 칸 추가 부분은 MySQL 전용 문법(`PREPARE`)이라 서버 PC에서 처음 확인하게 됩니다.

## 추가: 팔레트 2×4 반영 (통신 규약 v1.5.1, 11-20)

| 파일 | 바꾼 것 |
|---|---|
| `mqtt_db_writer.py` | `pallet_cell` 열 범위 0~4 → **0~3** (행 0~1 그대로). 칸 번호 `pallet_slot = 행 × 4 + 열 + 1` (1~8). 범위 밖 칸은 형식 오류로 거부 |
| 가짜 데이터 (`teamproject.sql`, `DB_변경_2026-11-17_주문.sql` 끝) | 회차마다 건전지 10개 → **8개** (칸 1~8). 건전지 54개, 회차 연결 11줄로 바뀜. 주문·재고·문의·인수인계·고객 정보 가짜 데이터는 그대로 |

- DB 테이블은 바꿀 것이 없습니다 (`pallet_slot`은 숫자 칸).
- 서버 PC: 저장 프로그램을 바꾸고, `DB_변경_2026-11-17_주문.sql`을 다시 실행하면 칸 9·10이 있던 예전 가짜 건전지가 지워지고 8개짜리로 다시 들어갑니다.
- 시험: 저장 프로그램 시험 44가지 통과 (칸 번호 1·4·5·8 확인, `[0,4]`·`[2,0]`·`[-1,0]` 거부 추가). 예전 가짜 데이터가 있는 서버 PC 상황에서 다시 실행해 66개 → 54개, 가장 큰 칸 번호 10 → 8 확인.

## 추가: 홈페이지 v8 확인 (11-20)

- 홈페이지 v8의 `order/new` 필드(`customer_type`, `age_group`, `region`)와 값이 이 문서의 형식과 같습니다. DB 칸 추가는 위 1~5장으로 이미 끝났습니다.
- 홈페이지는 지역을 고르지 않으면 `region: "none"`을 보냅니다. 저장 프로그램은 이 값을 경고 없이 받아 배송 주소로 지역을 채우고, 주소에 시·도가 없으면 `none`으로 저장합니다.
- 저장 프로그램 시험 47가지 통과 (`none` 처리, 시·도 17개 이름 확인 추가).

## 추가: 「주문 관리 프로그램 고객 유형·연령대·지역 반영」 제안에 맞춤 (11-20)

| 제안 | DB 쪽 처리 |
|---|---|
| `region` 기본값 `'none'`, NOT NULL | 반영. 모르는 지역은 NULL 대신 `none`. 11-20 첫 버전 스크립트를 이미 실행한 DB는 다시 실행하면 NULL → `none`으로 바꾸고 NOT NULL로 맞춤 |
| 값이 없거나 형식이 틀려도 주문 거절 안 함 | 반영. 저장 프로그램이 기본값으로 바꿔 저장 (예전에는 `customer_type`·`age_group`이 틀리면 거절했음) |
| 기업은 `age_group` 항상 `none` | 이미 반영 |
| `customer_type`·`age_group` VARCHAR(10) | **enum 유지 제안.** Core에서 읽을 때는 문자열 그대로라 차이가 없고, 다른 곳에서 DB에 직접 넣을 때 잘못된 값을 막아 줌. 값 목록은 제안과 같음 |
| mqtt_db_writer.py `OrderAccepted`·`INSERT` 세 칸 추가 (공통 항목) | **DB 담당이 이미 끝냄** (조시현 작업 불필요) |
| 가짜 주문에 세 값 섞기 | 이미 반영 (개인 24·기업 2, 연령대 6종, 지역 7곳) |

- 통계 쿼리의 지역별·순위 쿼리에서 `COALESCE(region, '미확인')`을 빼고 `region` 그대로 묶습니다 (`none`이 한 묶음).
- 저장 프로그램 시험 47가지 통과 (틀린 값 → 기본값, `none` 저장 반영).
