## 1. 공통 규칙

| 항목 | 규칙 |
|---|---|
| 브로커 | 서버 PC Mosquitto, 포트 1883 |
| 인코딩 | UTF-8 JSON |
| QoS | 발행 1, 구독 1 |

## 2. server/events — 장치·라인 이벤트

- 발행 시점: 장치 상태 변화, 라인 동작 변화 시 1건. 1초 주기 하트비트 자체는 발행하지 않음
- 브로커 연결이 끊긴 동안 발생한 이벤트: 발행 측에서 최대 1000건 보관 후 재연결 시 순서대로 발행

```json
{
  "event_id": "3ea1d8a266364241aa5e1b8a34f94dcb",
  "run_id": "20261112-093015-a3f9",
  "ts": "2026-11-12 09:40:12.481",
  "device": "arm1",
  "level": "ERROR",
  "message": "하트비트 5.2초 없음 → 끊김"
}
```

| 필드 | 타입 | 설명 |
|---|---|---|
| event_id | 문자열 32자 (16진수) | 이벤트 고유 번호. 재전송 시 동일 |
| run_id | 문자열 20자 | 중앙 서버 이벤트: 서버 실행 단위 번호 / 컨트롤러 이벤트: 회차 번호 |
| ts | 시각 | 발생 시각 |
| device | 문자열 ≤64 | `server`, `controller`, `arm1`(로봇팔 1, 통신 규약 v1.3까지 `pi`), `mega`, `env`(환경 Uno, v1.4.2), `yolo`, `agv`, `admin-<번호>`(예: `admin-01`, 통신 규약 v1.3까지 `ui-<PC이름>`). v1.4: 관리자 화면 이름 때문에 20 → 64자 |
| level | `INFO` / `WARN` / `ERROR` | 등급 |
| message | 문자열 ≤255 | 내용 |

| level | message 예 |
|---|---|
| INFO | 하트비트 수신 시작 → 정상 / 복구됨 (끊김 → 정상) / 회차 시작 / 회차 종료 |
| WARN | 하트비트 3.1초 없음 → 지연 / 하트비트 2개 빠짐 / YOLO 결과 없음 / Mega 서버 응답 대기 10초 (NO_RESPONSE) |
| ERROR | 하트비트 5.0초 없음 → 끊김 / 연결 끊김 (LWT) / pick 실패 / 퍽 순서 불일치 / 분류 실패 / 비상정지 |

## 3. server/results — 건전지 1개 최종 결과

- 발행 시점: Mega의 배출 완료 알림(`SORTED` 또는 재분류 `DIVERTED`) 수신 후 1건. 배출 실패(`FAULT`) 시에도 `dest = null`로 1건 발행
- v1.4: 벨트 위에 여러 퍽이 동시에 있으므로 결과는 battery_id 순서대로 오지 않을 수 있다 (예: 재분류 퍽이 앞 퍽보다 먼저 끝남)

```json
{
  "run_id": "20261112-093015-a3f9",
  "battery_id": 17,
  "pallet_cell": [0, 3],
  "picked_at": "2026-11-12 09:31:02.120",
  "vision": {"status": "ok", "result": "normal", "conf": 0.94, "polarity": "minus_up", "defects": []},
  "electrical_status": "measured",
  "polarity": "normal",
  "v_open": 1.582,
  "v_load": 1.491,
  "r_int": 0.603,
  "grade": "A",
  "reason": null,
  "dest": "AGV",
  "finished_at": "2026-11-12 09:31:20.480",
  "rule_version": "temp-2026-11-10",
  "r_load": 3.31
}
```

| 필드 | 타입 | 설명 |
|---|---|---|
| run_id | 문자열 20자 | 회차 번호 |
| battery_id | 정수 ≥1 | 회차 내 순번 |
| pallet_cell | [행, 열] | 팔레트 칸. 행 0~1, 열 0~2 (v1.4.5: 팔레트 2줄 × 3칸 = 6개. v1.4.3~v1.4.4는 열 0~3, v1.4.2까지 열 0~4) |
| picked_at | 시각 | 로봇팔 1 집기 시작 시각 |
| vision.status | `ok` / `failed` | `failed`: 카메라·모델 오류, 또는 **YOLO 결과 없음** (측정 자리에 도착할 때까지 결과가 안 옴) |
| vision.result | `normal` / `defect` / null | 앞·뒤 카메라를 합친 외관 판정 (규약 v1.2 3-2). **v1.4: 불량 이름 대신 `defect`** |
| vision.conf | 0~1 / null | 신뢰도 |
| vision.polarity | `minus_up` / `plus_up` / `unknown` / null | 세 카메라를 합친 극 방향 (위 카메라 우선) |
| vision.defects | 배열 | **v1.4 추가.** 불량 종류 목록 `[{"type": "scratch", "conf": 0.91, "cam": "front"}]`. 정상이면 `[]`, `failed`면 `[]` |
| vision.defects[].type | 문자열 ≤64 | 불량 종류: `scratch`(기스), `dent`(찌그러짐), `sticker`, … (YOLO 학습 클래스 이름, 영문 소문자) |
| vision.defects[].conf | 0~1 | 신뢰도 |
| vision.defects[].cam | `front` / `back` / `top` | 찾은 카메라 |
| electrical_status | `measured` / `skipped` / `failed` | 측정 완료 / 생략 / 실패 |
| polarity | `normal` / `reversed` / `abnormal` / null | 측정 극성. `measured`일 때만 값 |
| v_open | 소수 / null | 무부하 전압(V). `measured`이고 `reversed`가 아닐 때만 값 |
| v_load | 소수 / null | 부하 전압(V). `polarity = normal`일 때만 값 |
| r_int | 소수 / null | 내부저항(Ω). `polarity = normal`일 때만 값 |
| grade | `A` / `NG_VISUAL` / `NG_VOLTAGE` / `RESORT` | 새 회차 등급. `B`와 `NG`는 과거 이력에 남을 수 있다. |
| reason | 문자열 / null | 불량·재분류·배출 실패 사유 (고정 문장, 아래 표와 "배출 실패" 참고) |
| dest | `AGV` / `NG_VISUAL_BOX` / `NG_VOLTAGE_BOX` / `RESORT_BOX` / null | 실제 배출 위치. 배출 미완료 시 null. 과거 이력은 `B_BOX`와 `NG_BOX`를 포함할 수 있다. |
| finished_at | 시각 | 결과 확정 시각 |
| rule_version | 문자열 | 등급 판정 기준 버전 (v1.2 추가) |
| r_load | 소수 / null | 부하 저항 실측값(Ω). `polarity = normal`일 때만 값 (v1.2 추가) |

### 판정 순서 (위부터 적용)

| 순서 | 조건 | grade | dest | 전압 측정 | reason |
|---|---|---|---|---|---|
| 1 | 외관 검사 실패·YOLO 결과 없음 | RESORT | RESORT_BOX | 생략 | 외관 검사 실패 |
| 2 | 외관 불량 (거꾸로 포함) | NG_VISUAL | NG_VISUAL_BOX | 생략 | 외관 불량 |
| 3 | 위 카메라 기준 `plus_up` (외관 정상) | RESORT | RESORT_BOX | 생략 | +극이 위 |
| 4 | 측정 실패, `reversed`, `abnormal` | RESORT | RESORT_BOX | 시도 | 측정 실패 / 측정 극성 반대 / 접촉 불량 |
| 5 | 무부하 < 1.50V (내부저항과 관계없이, **개방전압 먼저**) | NG_VOLTAGE | NG_VOLTAGE_BOX | 완료 | 전압 낮음 |
| 6 | 무부하 ≥ 1.50V, 내부저항 ≤ 1.2Ω | A | AGV | 완료 | null |
| 7 | 무부하 ≥ 1.50V, 내부저항 > 1.2Ω | NG_VOLTAGE | NG_VOLTAGE_BOX | 완료 | 내부저항 큼 |

현재 임시 판정 기준 버전은 `temp-2026-11-25-no-b`다. `server/rules`로 발행한 기준은 DB `grading_rules`에 저장한다. 전압과 내부저항이 둘 다 기준을 벗어나면 사유는 "전압 낮음"이다.

### 경우별 값

| 경우 | electrical_status | polarity | v_open | v_load, r_int, r_load | grade | dest |
|---|---|---|---|---|---|---|
| 정상 측정 | measured | normal | 값 | 값 | A / NG_VOLTAGE | AGV / NG_VOLTAGE_BOX |
| 외관 불량 | skipped | null | null | null | NG_VISUAL | NG_VISUAL_BOX |
| YOLO 결과 없음 | skipped | null | null | null | RESORT | RESORT_BOX |
| 위 카메라 +극 위 | skipped | null | null | null | RESORT | RESORT_BOX |
| 측정 극성 반대 | measured | reversed | null | null | RESORT | RESORT_BOX |
| 측정 접촉 불량 | measured | abnormal | 값(0 근처) | null | RESORT | RESORT_BOX |
| 측정 실패 | failed | null | null | null | RESORT | RESORT_BOX |
| 배출 실패 | (판정 시점 값) | | | | (판정 등급) | null |

**배출 실패 reason**: Mega가 `FAULT`(`ARM2_FAILED` / `SERVO_FAILED`)를 보내면 등급은 판정한 그대로 두고 `dest = null`, reason은 판정 사유 뒤에 `배출 실패(<오류>)`를 붙인다.

| 판정 사유 | reason 예 |
|---|---|
| 없음 (A·B) | `배출 실패(ARM2_FAILED)` |
| 있음 | `전압 낮음, 배출 실패(ARM2_FAILED)`, `+극이 위, 배출 실패(SERVO_FAILED)` |

통계에서는 `배출 실패(`가 들어 있는지로 따로 셀 수 있다.

### 참고
- `reversed`일 때 `v_open = null`: 측정 입력 보호 다이오드가 음전압을 약 −0.25V에서 제한하여 측정값이 실제 전압과 다름 (하드웨어가 다이오드를 다시 넣기로 함 11/10, 지금 저장 프로그램 처리 그대로)
- 재분류함 건전지를 다시 투입하면 새 `battery_id`로 처리됨. 같은 실물이 2행으로 저장될 수 있음
- 집기 단계에서 작업자가 건너뛴 건전지는 결과를 발행하지 않음

## 4. event/estop — 비상정지

- 실제 버튼은 Arduino Mega에 연결. 버튼이 눌리면 Mega가 벨트·로봇팔 2를 직접 즉시 정지하고, 서버 PC의 Mega 중계 프로그램이 알림을 발행 (네트워크와 무관하게 정지)
- 발행 순서: 중계 `BUTTON_PRESSED` → 컨트롤러 `STOP_CONFIRMED` → 중계 `BUTTON_RELEASED` → (작업자 reset) → 컨트롤러 `RESET_CONFIRMED`
- 관리자 프로그램 비상정지(ui/cmd estop): 컨트롤러가 `source = WPF`로 `STOP_CONFIRMED`, `RESET_CONFIRMED` 발행
- 버튼이 눌린 상태에서는 reset 거부

```json
{
  "event_id": "9b1e0c4a5f2d4e6b8a7c3d2e1f0a9b8c",
  "run_id": "20261112-093015-a3f9",
  "ts": "2026-11-12 09:40:12.481",
  "device": "mega",
  "button_id": "estop_1",
  "source": "PHYSICAL_BUTTON",
  "kind": "BUTTON_PRESSED",
  "details": null
}
```

| 필드 | 타입 | 설명 |
|---|---|---|
| event_id | 문자열 32자 | 고유 번호 |
| run_id | 문자열 20자 / null | 진행 중인 회차. 회차 전이면 null |
| ts | 시각 | 발생 시각 |
| device | 문자열 | `mega`(버튼), `controller`(확인). v1.3까지는 `pi` |
| button_id | 문자열 / null | 버튼 이름. WPF 비상정지면 null |
| source | `PHYSICAL_BUTTON` / `WPF` / `OTHER` | 비상정지 원인 |
| kind | `BUTTON_PRESSED` / `BUTTON_RELEASED` / `STOP_CONFIRMED` / `RESET_CONFIRMED` | 종류 |
| details | 문자열 ≤512 / null | 부가 설명 (예: Mega 정지 응답 없음) |

## 5. sensor/env — 환경 센서

- 센서는 **환경 Uno**에 연결 (통신 규약 v1.5, v1.4까지는 Mega). Uno가 주기적으로(기본 5초) 보내고 환경 중계 프로그램(`env_relay.py`)이 이 형식으로 발행. 메시지 1건에 여러 측정값. `readings` 1개 = DB 1행
- 가스 센서는 MQ-9 → Uno 아날로그 핀 원시값(10비트 0~1023), 단위 `raw`
- 온습도 센서 모델, 경고 기준값은 하드웨어 담당 확정 전

```json
{
  "reading_id": "4c2a…32자",
  "run_id": "20261112-093015-a3f9",
  "ts": "2026-11-12 09:40:15.000",
  "device": "env",
  "readings": [
    {"sensor": "gas_1", "metric": "GAS", "value": 182, "unit": "raw"},
    {"sensor": "temp_hum_1", "metric": "TEMPERATURE", "value": 24.1, "unit": "C"},
    {"sensor": "temp_hum_1", "metric": "HUMIDITY", "value": 41.0, "unit": "%"}
  ]
}
```

| 필드 | 타입 | 설명 |
|---|---|---|
| reading_id | 문자열 32자 | 측정 묶음 번호. 같은 메시지 안의 값은 같은 번호 |
| run_id | 문자열 20자 / null | 진행 중인 회차 |
| ts | 시각 | 측정 시각 |
| device | 문자열 | `env` (v1.5, 환경 Uno). v1.4까지는 `mega`, v1.3까지는 `pi` |
| readings[].sensor | 문자열 ≤64 | 센서 이름 |
| readings[].metric | `GAS` / `TEMPERATURE` / `HUMIDITY` | 측정 종류 |
| readings[].value | 소수 | 측정값 |
| readings[].unit | 문자열 ≤24 | 단위 |

## 5-1. server/rules — 판정 기준값 (v1.4.4, 11/21)

라인 컨트롤러가 **브로커에 연결될 때와 회차를 시작할 때** 발행 (QoS 1, **retained**). DB 저장 프로그램이 `grading_rules`에 저장한다 (DB 쓰기는 저장 프로그램만, 11/20 결정 ⑤⑩). 검사 성적서(주문 관리 F6)는 결과의 `rule_version` → `battery_cycles.rule_id` → `grading_rules`로 **그 회차의 기준값**을 읽는다 (성적서 합격 기준 = 라인 A 기준, 결정 ⑩).

```json
{
  "rule_version": "temp-2026-11-25-no-b",
  "effective_at": "2026-11-25 00:00:00.000",
  "thresholds": {
    "A": {"v_open_min": 1.50, "r_int_max": 1.2},
    "order": "v_open_first"
  },
  "ts": "2026-11-25 09:53:25.041"
}
```

| 필드 | 형식 | 설명 |
|---|---|---|
| rule_version | 문자열 ≤40 | `server/results`의 `rule_version`과 같은 값 |
| effective_at | 시각 | 이 기준을 쓰기 시작한 시각 |
| thresholds.A | `{v_open_min, r_int_max}` | 무부하 전압 최소(V), 내부저항 최대(Ω). 과거 버전에는 `thresholds.B`가 있을 수 있다. |
| thresholds.order | `"v_open_first"` | 무부하 전압을 먼저 보고 내부저항 기준을 확인한다 (3장 표). |
| ts | 시각 | 발행 시각 (DB에는 저장 안 함) |

- 같은 `rule_version`은 값이 바뀌지 않는다. 저장된 버전에 다른 값이 오면 저장 프로그램은 바꾸지 않고 경고만 남긴다 → 값을 바꿀 때는 `rule_version`을 새로
- 결과가 기준보다 먼저 와서 `rule_version`만 있는 행이 만들어졌으면, 나중에 온 `server/rules`가 빈 칸(`voltage_and_resistance_thresholds`, `effective_at`)을 채운다

## 6. 명령·응답 원문 (communication_logs)

새 토픽 없음. DB 저장 프로그램이 기존 토픽을 구독해 원문 기록.

| 토픽 | message_kind | 칸에 넣을 값 |
|---|---|---|
| `cmd/<장치>` | COMMAND | device = 토픽 뒤 이름, cmd_id, run_id → source_run_id, battery_id → source_battery_id, action, ts → sent_at |
| `res/<장치>` | RESPONSE | device, cmd_id, status → response_status, error → error_text, ts → sent_at |
| `ui/cmd` | OPERATOR_COMMAND | action, ts → sent_at. 선택 필드 `by`(로그인 아이디)는 `payload_text`의 원문 JSON에 저장 |

공통: topic, MQTT qos·dup·retain 플래그, payload_text = 원문 JSON. 명령과 응답은 `(device, cmd_id)`로 연결.

**선택 (DB 담당 가능 여부 확인 중)**: `vision/result`, `event/mega`, `event/env`(v1.4.2, 환경 경고)도 원문 기록. message_kind에 `EVENT` 추가 필요. 칸: device = `yolo` / `mega` / `env`, `no` → source_battery_id, `ev` → action, ts → sent_at
