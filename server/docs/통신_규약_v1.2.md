# 통신 규약 v1.2

작성: 중앙 서버·통신 담당 조시현 · 2026-11-06
상태: **v1.2 (2026-11-10)**. 하드웨어·DB·팀 답변(11/10)과 YOLO 담당 결정을 반영. 서버 PC 통합 시험 통과(11/10). 메시지 형식은 확정이며, 남은 ❓(7장)는 실제 구동 후 정할 값과 AGV 세부. 모든 장치·프로그램은 이 문서의 토픽·메시지 형식을 기준으로 구현한다. 바꿔야 하면 통신 담당에게 알리고 버전을 올린다

**표시**
| 표시 | 뜻 |
|---|---|
| ❓ 팀 결정 필요 | 아직 정하지 않음. 정해지면 메시지 형식이 바뀔 수 있음 (7장 목록) |
| 🟡 임시값 | 값은 정했지만 시험 후 바뀔 수 있음 |
| ⚠ | 라인 동작·배선에 대한 확인 사항 (메시지 형식 영향 없음) |

## 0. 한눈에

```
[서버 PC]
  Mosquitto(브로커) ── 모든 프로그램이 여기에만 접속
  중앙 서버 ─────────── 장치 감시 (하트비트)
  라인 컨트롤러 ─────── 퍽 순서 관리, 계획(PLAN)·보낼 곳 결정, 등급 판정
  YOLO 프로그램 ─────── 팔레트 인식, 검사 부스 결과를 스스로 전송 (vision/result)
  Mega 중계 프로그램 ── cmd/mega ↔ USB 시리얼 ↔ Arduino Mega
  WPF 관리자 프로그램 ─ 현재 상태 표시, 시작/정지 버튼
  DB 저장 프로그램 ──── MySQL 저장
[로봇팔 1: myCobot 280-PI] ── 내장 라즈베리파이가 cmd/pi를 직접 받음 (팔레트 → 벨트, 퍽째)
[Arduino Mega] ── 서버 PC에 USB. 컨베이어, 측정 헤드, 재분류 서보, 로봇팔 2(MYLOOP+전자석), 도착 센서,
                   비상정지 버튼, 가스·온습도 센서, 부저
[AGV 중계 프로그램] ─── 블루투스 ↔ MQTT
```
- 팔 1과 Mega는 서로 직접 연결하지 않고, 각자 서버와 따로 연결한다 (하드웨어 확정 11/10)
- Mega 중계 프로그램과 YOLO는 **서버 PC**에서 돈다 (하드웨어 확정 11/10)

**기본 원칙**
1. **서버만 명령한다.** 장치끼리 직접 명령하지 않는다.
2. **장치는 자기 일만 한다.** "어디로 보내라"는 서버가, "언제·어떻게 움직이나"는 장치가 정한다. (예: 벨트 속도, 팔 2가 집는 시점은 Mega가 계산)
3. **명령에는 응답이, 장치가 스스로 겪은 일에는 알림이 온다.** v1.2부터 YOLO와 Mega는 명령 없이도 알림(`vision/result`, `event/mega`)을 보낸다.
4. **물리 동작은 서버가 자동으로 재시도하지 않는다.** 실패하면 멈추고 작업자가 판단한다.

## 1. 공통 규칙

| 항목 | 규칙 |
|---|---|
| 브로커 | 서버 PC의 Mosquitto, 포트 1883 |
| 메시지 형식 | UTF-8 JSON (메시지 하나 = JSON 한 개) |
| 시각 | 서버 PC 한국 시간 `YYYY-MM-DD HH:MM:SS.mmm` (하트비트의 `ts`만 유닉스 초). Mega 메시지의 시각은 PC 중계 프로그램이 붙인다 |
| QoS | 하트비트 0, 그 외 전부 1 |
| retained | `status/*`, `server/devices`, `server/line`만 사용 |
| client_id | `server`, `controller`, `pi`(로봇팔 1), `mega`(Mega 중계), `yolo`, `agv`, `db_saver`. 관리자 프로그램은 `ui-<PC이름>` |
| run_id | 회차 번호. 라인 컨트롤러가 `start` 때마다 새로 만든다 (회차 = 팔레트 한 판) |
| battery_id | 회차 안에서 서버가 매기는 건전지 번호 (1부터). **`pick` 명령 때 부여하며, 퍽 순서의 기준이다.** Mega 메시지의 `no`와 같은 값 |

### 토픽 이름 규칙
| 형태 | 방향 | 용도 |
|---|---|---|
| `cmd/<장치>` | 서버 → 장치 | 명령 |
| `res/<장치>` | 장치 → 서버 | 명령에 대한 응답 |
| `vision/result` | YOLO → 서버 | 검사 부스 결과 알림 (v1.2) |
| `event/mega` | Mega 중계 → 서버 | 퍽 도착·측정·분류 알림 (v1.2) |
| `hb/<장치>` | 양쪽 | 하트비트 (1초) |
| `status/<장치>` | 각자 | online / offline (LWT) |
| `server/...` | 서버 → 화면·DB | 상태, 이벤트, 결과 |
| `ui/cmd` | 화면 → 서버 | 작업자 버튼 |

## 1-1. 지휘 프로그램 분리 (v0.9.3)

- 순서·판정을 맡는 **라인 컨트롤러(`line_controller.py`, client_id `controller`)**를 중앙 서버(`central_server.py`, 장치 감시·이벤트)와 별도 프로그램으로 둔다.
- 컨트롤러도 `hb/controller` 하트비트와 `status/controller` LWT를 보낸다.
- 컨트롤러는 `server/devices`를 구독해 pi·mega·yolo가 지연·끊김이 되면 새 퍽을 올리지 않고 일시정지한다.

## 2. 명령과 응답 (cmd / res)

### 명령 형식 — `cmd/<장치>`
```json
{"cmd_id": "7f3a9c1e02b44d8e", "run_id": "20261112-093015-a3f9", "battery_id": 17,
 "action": "pick", "params": {"cell": [0, 3]}, "ts": "2026-11-12 09:31:00.120"}
```

### 응답 형식 — `res/<장치>`
```json
{"cmd_id": "7f3a9c1e02b44d8e", "status": "done", "data": {}, "error": null, "ts": "2026-11-12 09:31:06.874"}
```

| status | 뜻 | 언제 보내나 |
|---|---|---|
| `accepted` | 명령 받음, 시작함 | 받자마자 (1초 안) |
| `done` | 성공적으로 끝남 | 동작이 끝났을 때. 결과값은 `data`에 |
| `failed` | 시도했지만 실패 | `error`에 이유 |
| `rejected` | 시작하지 않음 | 다른 명령 실행 중, 비상정지 상태 등 |

**장치가 지킬 것**
- 같은 `cmd_id`가 다시 오면 다시 실행하지 말고 마지막 응답을 다시 보낸다.
- `estop`은 언제나 즉시 실행한다.

**서버가 지킬 것 (시간 제한, 🟡 임시값)**: accepted까지 2초, done/failed까지는 각 명령 표. 시간 초과 시 라인 일시정지 + ERROR 이벤트

## 3. 장치별 명령

### 3-1. 로봇팔 1 (myCobot 280-PI) — `cmd/pi`, `res/pi`

| action | params | done의 data | 제한 시간(🟡) | 하는 일 |
|---|---|---|---|---|
| `pick` | `{"cell": [행, 열]}` | `{}` | 20초 | 팔레트 칸에서 **퍽과 건전지를 통째로** 집어 벨트에 올림 |
| `estop` | `{}` | `{}` | 즉시 | 로봇팔 정지 |
| `reset` | `{}` | `{}` | 30초 | 비상정지 해제 후 원점 복귀 |

- 하트비트: `hb/pi`: `{..., "arm": "ok" / "stopped"}`
- `pick`의 `done` = 퍽이 벨트에 놓임. 서버는 이때 그 `battery_id`를 **벨트 위 퍽 줄**의 맨 뒤에 넣는다.

### 3-1-1. Arduino Mega — `cmd/mega`, `res/mega`, `event/mega`

```
서버 ──MQTT(cmd/mega)──▶ Mega 중계(PC) ──USB 시리얼(JSON 한 줄)──▶ Mega ──▶ 컨베이어, 측정 헤드, ADS1115, 부하 MOSFET,
서버 ◀─MQTT(res/mega, event/mega)── Mega 중계 ◀──USB 시리얼────── Mega       재분류 서보, 로봇팔 2, 도착 센서, 비상정지 버튼
```
- Mega는 MQTT를 쓸 수 없어 USB 시리얼로만 연결한다. PC의 중계 프로그램이 시리얼 ↔ MQTT를 바꾸고 **시각(`ts`)을 붙인다.**
- 중계 ↔ Mega 시리얼은 JSON 한 줄씩 (하드웨어 확정). 세부 키 이름은 하드웨어 담당이 정하고, 중계 프로그램이 이 규약의 MQTT 형식으로 바꾼다.
- 벨트는 **Mega가 직접 켜고 끈다.** 측정 자리 센서에서만 멈출 수 있고, 로봇팔 2가 집을 때는 멈추지 않는다 (측정 자리 출발 후 경과 시간으로 집는 시점을 맞춤).
- 벨트 속도는 Mega가 PWM으로 조절한다: 평소 빠르게, 측정 자리·집는 자리 근처에서만 느리게.
- 걸리는 시간 (🟡 하드웨어 추정 11/10, 실제 구동 후 갱신)
  | 구간 | 시간 | 내역 |
  |---|---|---|
  | 측정 자리 도착 → 측정 끝 | 약 4~5초 | 헤드 내림 1.7초 + 측정 0.4초 + 헤드 올림 1.7초 + 서버 응답 |
  | 측정 자리 출발 → 분류 완료 | 약 12~15초 | 이동 약 6초 + 로봇팔 2 집고 놓기 약 5~8초 |
  | 검사 부스 → 측정 자리 | ❓ | 서버가 PLAN을 이 시간 안에 보내야 함 (서버 처리는 수 ms) |
- 하트비트 `hb/mega`: `{..., "serial": "ok" / "offline", "belt": "run" / "stop", "queue": 2}` (`queue` = Mega가 들고 있는 계획 개수)
  - Mega는 시리얼로 1초마다 하트비트를 보낸다. 끊기면 중계가 `serial: "offline"`으로 바꿔 서버에 알린다 (하드웨어 확정 11/10)
- 센서 (하드웨어 확정 11/10): 퍽 도착 센서 TCRT5000 2개(측정 자리: 정지·시간 기준 / 집는 자리: 실패 감지), 측정 헤드 위쪽 리밋 스위치 1개(헤드가 올라온 것이 확인돼야 벨트 출발)
- 서버 하트비트(`hb/server`)가 3초 이상 끊기면 중계가 Mega에 벨트 정지를 보낸다.

**명령 (서버 → Mega)**
| action | params | done의 data | 제한 시간(🟡) | 하는 일 |
|---|---|---|---|---|
| `plan` | `{"no": 17, "act": "PASS" / "MEASURE", "to": "NG_VISUAL_BOX" / "RESORT_BOX" / null}` | `{}` | 2초 | 퍽 하나의 계획을 Mega의 계획 줄 맨 뒤에 넣음 |
| `route` | `{"no": 17, "to": "AGV" / "B_BOX" / "NG_VOLTAGE_BOX" / "RESORT_BOX"}` | `{}` | 2초 | 측정이 끝난 퍽의 보낼 곳. 받으면 벨트 다시 출발. `RESORT_BOX`는 측정에서 거꾸로·접촉 불량·측정 실패일 때 (서보로 쳐냄) |
| `belt` | `{"run": true}` | `{}` | 2초 | 벨트 켜기 (라인 시작·재개) |
| `belt` | `{"run": false}` | `{}` | 2초 | **일시정지**: 그 자리에 멈춤. 측정 중이거나 로봇팔 2가 움직이는 중이면 그 동작만 끝내고 멈춤 |
| `belt` | `{"run": false, "drain": true}` | `{}` (벨트 위 퍽을 모두 분류한 뒤 done) | 60초 🟡 | **종료**: 벨트 위 퍽을 모두 분류한 뒤 멈춤. 그동안 서버는 로봇팔 1에 새 `pick`을 보내지 않음. 서버는 벨트 위 **모든 퍽의 `plan`을 보낸 뒤** drain을 보낸다 (Mega는 계획을 받은 퍽만 알기 때문) |
| `estop` | `{}` | `{}` | 즉시 | 컨베이어 전원 차단, 로봇팔 2 정지, 부하 끔 |
| `reset` | `{}` | `{}` | 30초 | 비상정지 해제 후 원점 복귀, 계획 줄 비움 |

- `plan`의 `act`
  | act | 언제 (서버가 YOLO 결과로 정함) | `to` | 측정 자리에서 |
  |---|---|---|---|
  | `PASS` | 외관 불량 (거꾸로 + 외관 불량 포함) | `NG_VISUAL_BOX` | **멈추지 않고 통과** → 팔 2가 외관불량함에 넣음 |
  | `PASS` | 거꾸로만 (외관 정상, 위 카메라 `plus_up`) | `RESORT_BOX` | **멈추지 않고 통과** → 측정 자리 뒤 서보가 퍽째 쳐냄 |
  | `MEASURE` | 정상 (외관 정상, `minus_up` 또는 `unknown`) | `null` (측정 후 `route`로 정함) | 멈춤 → 측정 → `MEASURED` 알림 → `route` 기다림 |
- Mega는 측정 자리 센서에 퍽이 오면 **계획 줄 맨 앞**을 꺼내 그대로 따른다.
- **계획이 아직 없으면** 벨트를 멈추고 `WAIT_PLAN` 알림을 보낸다. 서버는 YOLO 결과가 없는 것을 확인하고 `plan`(`PASS`, `RESORT_BOX`)으로 답한다 (하드웨어 확정 11/10).
- 서버 응답(`plan`·`route`)이 없으면 Mega는 측정 자리에서 **계속 정지·대기**하고, 10초가 지나면 중계가 `NO_RESPONSE` 알림을 보낸다 (하드웨어 확정). 컨트롤러는 이를 `server/events` WARN으로 바꿔 관리자 화면에 경고를 띄운다. 컨트롤러 자체가 죽은 경우는 중앙 서버의 하트비트 감시가 "controller 끊김"으로 알린다.

**알림 (Mega → 서버) — `event/mega`**
```json
{"ev": "MEASURED", "no": 17, "seq": 42, "data": {"polarity": "normal", "v_open": 1.4429, "v_load": 1.1800,
 "r_load": 3.300, "r_int": 0.735}, "ts": "2026-11-12 09:31:12.300"}
```
| ev | no | data | 언제 |
|---|---|---|---|
| `WAIT_PLAN` | null | `{}` | 측정 자리에 퍽이 왔는데 계획이 없어 벨트를 멈춤 |
| `MEASURED` | 번호 | 측정값 (아래 표) | `MEASURE` 퍽 측정 끝. 벨트는 멈춘 채 `route`를 기다림 |
| `DIVERTED` | 번호 | `{}` | 서보가 퍽째 재분류함으로 쳐냄 |
| `AT_PICK` | 번호 | `{}` | 퍽이 로봇팔 2가 집는 자리에 도착. **센서가 아니라** 측정 자리를 지난 뒤 벨트가 움직인 시간으로 Mega가 계산한 값 |
| `NO_RESPONSE` | 번호 / null | `{"waiting": "plan" / "route"}` | 측정 자리에서 서버 응답을 10초 넘게 기다리는 중 (계속 대기) |
| `SORTED` | 번호 | `{"to": "AGV"}` (실제로 넣은 곳) | 로봇팔 2가 건전지를 함에 넣음 = **배출 완료** |
| `FAULT` | 번호 / null | `{"error": "종류"}` (아래 표) | 장치 이상. 서버는 라인을 일시정지하고 관리자 화면에 표시 |
| `ENV_ALARM` | null | `{"sensor": "gas_1", "value": 612}` | 가스·온습도 기준 초과 (Mega가 부저도 울림) |

**FAULT 종류** (하드웨어 확정 11/10)
| error | 감지 방법 |
|---|---|
| `SENSOR_TIMEOUT` | 계획은 있는데 측정 자리 센서에 퍽이 올 시간이 지나도 안 옴 |
| `ARM2_FAILED` | 집는 자리 센서: 로봇팔 2가 집은 뒤에도 건전지가 남아 있음 |
| `SERVO_FAILED` | 집는 자리 센서: 재분류로 쳐냈어야 할 퍽이 집는 자리에 옴 |
| `HEAD_FAILED` | 헤드 위쪽 리밋 스위치: 올림 후 안 눌림, 또는 내림 후 안 떨어짐 |
| `ADC_FAILED` | 측정기(ADS1115) 통신 오류 |
- "계획 없이 퍽 도착"은 `WAIT_PLAN`으로 보낸다. 계획과 퍽의 짝이 맞는지는 서버가 `no`와 순서로 판단한다
- 비상정지 버튼은 `FAULT`가 아니라 `event/estop`으로 보낸다 (3-4)
- `seq`: **Mega 자체** 알림 일련번호 (1부터, 재시작 시 1). 서버 건전지 번호와는 별개이며, 서버가 빠진 알림을 찾는 데 쓴다.
- 로봇팔 2는 흐르는 벨트에서 고정 좌표로 집는다. 벨트가 멈추는 곳은 측정 자리 한 곳뿐이다.
- `no`는 Mega가 계획에서 받은 번호를 그대로 돌려준다. 서버는 이 번호로 퍽 줄 순서가 맞는지 확인하고, 다르면 라인을 일시정지한다.

**측정값 (`MEASURED`의 data)** — 극성 판단·내부저항 계산은 Mega가 한다
| polarity | 조건(🟡) | 부하 측정 | v_open | v_load, r_int, r_load |
|---|---|---|---|---|
| `normal` | v_open ≥ 0.1V | 함 | 숫자 | 숫자 |
| `reversed` | v_open < −0.1V (+극이 위) | **안 함** | **null** | null |
| `abnormal` | −0.1V ~ 0.1V (접촉 불량 등) | **안 함** | 숫자(0 근처) | null |
- v1.2 변경: 하드웨어 쪽에서 입력 보호 다이오드를 다시 추가하므로(11/10), 거꾸로일 때 측정값이 약 −0.25V에서 잘린다. 값이 의미 없으므로 v1.0처럼 `reversed`면 `v_open`을 null로 보낸다 (극성 판단에는 충분)
- 측정 회로: ADS1115 A0−A1 차동, 측정 헤드는 전기 실린더 + 포고핀. 무부하 약 0.5초, 부하 0.3~0.4초
- 접촉 불량(`abnormal`)·측정 실패는 Mega가 **한 번 다시 측정**하고, 그래도 같으면 보고한다 (하드웨어 확정 11/10)
- 측정 실패: `MEASURED`의 data에 `{"polarity": null, "error": "ADC_FAILED"}`. **부하 MOSFET은 실패해도 반드시 끈 뒤 알림.**
- 측정 후 재분류(거꾸로·접촉 불량·측정 실패)는 서버가 `route`로 `RESORT_BOX`를 보내고, Mega가 측정 자리 다음의 서보로 퍽째 쳐낸다 (하드웨어 확정 11/10)
- ⚠ 하드웨어 안전 확인: 거꾸로 닿았을 때 IRLZ44N 내부 다이오드를 통한 전류

### 3-2. YOLO — `cmd/yolo`, `res/yolo`, `vision/result`

| action | params | done의 data | 제한 시간(🟡) |
|---|---|---|---|
| `scan_pallet` | `{}` | `{"cells": [[0,0],[0,1],[1,3]], "conf": [0.97,0.95,0.91]}` | 5초 |

- `cells`: 건전지가 **있는** 칸만, [행, 열] (팔레트 2×5, 왼쪽 위가 [0,0])
- ❓ 팔레트 칸을 집는 순서 (시험 후 결정)

**검사 부스 결과 — `vision/result` (명령 없이 YOLO가 스스로 전송, YOLO 담당 결정 11/10)**
```json
{"seq": 42, "status": "ok", "result": "defect", "conf": 0.91, "polarity": "minus_up",
 "defects": [{"type": "scratch", "conf": 0.91, "cam": "front"}],
 "sides": [{"cam": "front", "result": "defect", "conf": 0.91, "polarity": "minus_up"}],
 "ts": "2026-11-12 09:31:08.120"}
```
| 필드 | 설명 |
|---|---|
| `seq` | YOLO가 매기는 결과 일련번호 (1부터, 재시작 시 1) |
| `status` | `ok` / `failed` (카메라 오류·신뢰도 미달 → `error`에 이유) |
| `result`, `conf` | 앞·뒤 카메라를 합친 외관 판정: `normal` / `defect` |
| `defects` | 불량 종류 목록 `[{"type", "conf", "cam"}]`. 정상이면 `[]`. 종류가 늘어도 형식은 그대로 (하드웨어 제안 11/10) |
| `polarity` | 세 카메라를 합친 극 방향 `minus_up` / `plus_up` / `unknown` |
| `sides` | (선택) 카메라별 원래 결과. `cam`: `front` / `back` / `top` |

- 카메라 3대 (부스 안 고정): **앞·뒤 = 외관 + 극 방향, 위 = 극 방향**
- 보내는 시점: 퍽이 앞 카메라 화면의 기준선을 지날 때 세 카메라로 판정해 **퍽 하나당 1건**
- 외관 합치기: 한 대라도 불량이면 불량(두 대 모두 불량이면 신뢰도 높은 쪽), 둘 다 정상이면 정상(conf는 낮은 값)
- 극 방향 합치기: **위 카메라가 신뢰도 기준 이상이면 위 카메라 값 → 아니면 앞·뒤가 같은 값일 때만 채택 → 그 외 `unknown`**
- 중복 방지: 추적 번호로 같은 퍽은 한 번만, 벨트 속도로 계산한 최소 간격 안의 두 번째 결과는 버림
- 불량 종류(`defects[].type`): `scratch`(기스), `dent`(찌그러짐), `sticker`. 그 밖은 YOLO 학습 클래스 이름 그대로 (영문 소문자, 64자 이하). DB `visual_defects`가 건전지 하나에 여러 행을 받을 수 있어 종류별로 저장 가능
- 서버는 결과를 **벨트 위 퍽 줄에서 아직 YOLO 결과가 없는 가장 앞 퍽**에 붙인다. 붙일 퍽이 없는데 결과가 오면(중복·유령) 버리고 WARN 이벤트를 남긴다.
- 🟡 신뢰도 기준, 기준선 위치, 최소 간격은 실물 시험 후 정함

### 3-4. 비상정지 버튼·환경 센서

| 장치 | 연결 | 토픽 | 방향 |
|---|---|---|---|
| 비상정지 버튼 | Mega (중계 뒤 시리얼) | `event/estop` | 중계 → 컨트롤러·DB·관리자 프로그램 |
| 가스·온도·습도 센서 | Mega (중계 뒤 시리얼) | `sensor/env` | 중계 → DB·관리자 프로그램 |

- 버튼이 눌리면 Mega가 벨트·로봇팔 2를 즉시 멈추고 서버에 알린다. MQTT 메시지는 정지 후 알림이다.
- ⚠ 하드웨어 확인: 가능하면 모터 12V 전원도 버튼으로 직접 차단 (Mega 코드와 관계없이 멈추도록)
- 컨트롤러는 `BUTTON_PRESSED`를 받으면 회차를 멈추고 `cmd/pi estop`, `cmd/mega estop`을 보낸 뒤 `STOP_CONFIRMED`를 발행한다. 버튼이 눌린 동안 `reset` 거부.
- 비상정지 메시지의 `device`는 `mega`. 메시지 형식과 DB 대응: 메시지_형식 4~5장
- 환경 센서는 Mega가 주기적으로(🟡 5초) JSON으로 보내고, 중계가 `sensor/env` 형식(`device: "mega"`, `reading_id`, `ts`)으로 바꿔 발행한다
- 가스 센서 MQ-9: Mega 아날로그 핀 원시값, `sensor: "gas_1"`, `unit: "raw"`. 온습도 DHT11: `temp_hum_1`, `C` / `%`. 센서는 더 늘어날 수 있음 (형식 그대로, `sensor` 이름만 추가)
- 기준 초과 시 Mega가 부저를 울리고 `event/mega`로 `ENV_ALARM`을 보낸다
- 부저는 Mega에 연결 (경고음 조건은 하드웨어 담당이 정함, 서버 명령 없음)

## 4. 건전지 처리 흐름 (서버가 퍽 줄로 관리)

```
서버(컨트롤러)                 팔 1(pi)          YOLO                 Mega
 │ scan_pallet ─────────────────────────────▶ │
 │ battery_id 부여, pick {cell} ──▶ │ 퍽째 벨트에 올림
 │ ◀──────────── done ─────────────│  → 퍽 줄 맨 뒤에 추가
 │                                  (벨트가 흘러 검사 부스 통과)
 │ ◀──────────────── vision/result ─────────│  → 줄에서 결과 없는 첫 퍽에 붙임
 │ 계획 결정 ─── plan {no, act, to} ─────────────────────────────▶ │ 계획 줄에 추가
 │                                                                 │ 측정 자리 센서
 │                                                                 │  PASS: 통과
 │                                                                 │  MEASURE: 정지 → 측정
 │ ◀──────────────────────────────── event/mega MEASURED ──────────│
 │ 등급 판정 ── route {no, to} ──────────────────────────────────▶ │ 벨트 다시 출발
 │ ◀──────────────────── event/mega DIVERTED / AT_PICK / SORTED ───│
 │ server/results 발행 → DB 저장 (SORTED·DIVERTED = 배출 완료)
```
- 여러 퍽이 동시에 벨트 위에 있을 수 있다. 서버는 퍽 줄(battery_id 순서)로 각 퍽의 단계를 따로 관리한다.
- 새 퍽 올리기(`pick`)는 벨트 위 퍽 수가 `MAX_ON_BELT`(🟡) 미만일 때만 한다.
- 계획이 없어 `WAIT_PLAN`이 오면: 줄 맨 앞 퍽에 YOLO 결과가 없으면 `vision.status = failed`로 기록하고 `plan`(`PASS`, `RESORT_BOX`)을 보낸다.

**판정 (서버) — 위에서부터 차례로. 판정 순서는 팀 확정, 전압 기준값은 🟡 임시값**
| 순서 | 조건 | 등급 | dest | 측정 | 옮기는 방법 |
|---|---|---|---|---|---|
| 1 | YOLO 결과 없음·검사 실패 | RESORT | `RESORT_BOX` | 안 함 | 서보 |
| 2 | 외관 불량 (거꾸로 포함) | **NG_VISUAL** | `NG_VISUAL_BOX` (외관불량함) | 안 함 | 팔 2 |
| 3 | 거꾸로 (`plus_up`, 외관 정상) | RESORT | `RESORT_BOX` (재분류함) | 안 함 | 서보 |
| 4 | 측정 결과 reversed / abnormal / 측정 실패 | RESORT | `RESORT_BOX` | 함 | 서보 |
| 5 | 무부하 ≥ 1.50V, 내부저항 ≤ 0.9Ω 🟡 | A | `AGV` (A 적재 자리) | 함 | 팔 2 |
| 6 | 무부하 ≥ 1.30V, 내부저항 ≤ 1.5Ω 🟡 | B | `B_BOX` | 함 | 팔 2 |
| 7 | 그 외 | **NG_VOLTAGE** | `NG_VOLTAGE_BOX` (전압불량함) | 함 | 팔 2 |

- 등급: `A`, `B`, `NG_VISUAL`(외관이상), `NG_VOLTAGE`(전압이상), `RESORT`(재분류). 기존 `NG`는 이전 데이터용 (DB 반영 완료 11/10)
- 기준값을 바꾸면 결과의 `rule_version`도 바꾼다
- `unknown`(극 방향 애매)은 측정으로 보낸다. 거꾸로면 측정 자리에서 걸러진다 (2중 확인)

**실패하면**
| 실패 | 서버 동작 |
|---|---|
| pick 실패 | 새 퍽 올리기 멈춤, ERROR 이벤트. 작업자가 "재개/건너뛰기" 선택 |
| YOLO 결과 없음 | `WAIT_PLAN`에 RESORT 계획으로 답함 (위 1번) |
| 측정 실패 | 측정 실패 → RESORT |
| `no`가 퍽 줄 순서와 다름 | 라인 일시정지, ERROR 이벤트 (작업자가 벨트 위 퍽 정리) |
| `FAULT` (ARM2_FAILED·SERVO_FAILED) | 그 퍽은 dest = null, reason에 `배출 실패(<오류>)`를 붙여 결과 저장, 라인 일시정지 |
| `FAULT` (그 밖) | ERROR 이벤트, 라인 일시정지 |
| `ENV_ALARM` | WARN 이벤트 (라인은 계속) |
| `NO_RESPONSE` 알림 | WARN 이벤트 (관리자 화면 경고), 라인 일시정지 (새 퍽 안 올림, `belt run:false`). 원인 확인 후 작업자가 재개 |
| 명령 응답 시간 초과 (`plan`·`route` 2초 등, 2장 표) | ERROR 이벤트, 라인 일시정지 |
| 배출 완료 지연 (🟡 퍽을 올린 뒤 60초 안에 `SORTED`·`DIVERTED`가 없음) | ERROR 이벤트, 라인 일시정지 |
| 비상정지 | 벨트 위 퍽은 결과 없이 정리 (작업자가 회수), WARN 이벤트로 번호 기록 |
| 장치 끊김 (하트비트) | 라인 일시정지 |

## 5. 작업자 화면 (WPF) ↔ 서버

### `ui/cmd` — 화면 → 서버 (버튼)
| action | 뜻 |
|---|---|
| `start` | 라인 시작 (벨트 켜기, 퍽 올리기 시작) |
| `pause` / `resume` | 일시정지 / 재개 (`belt run:false` → 그 자리 정지, 새 퍽 안 올림) |
| `stop` | 회차 종료 (새 퍽 안 올림 → `belt run:false, drain:true`로 벨트 위 퍽을 모두 분류한 뒤 종료) |
| `estop` | 비상정지 (즉시 `cmd/pi`, `cmd/mega` estop 전달) |
| `reset` | 비상정지 해제 |
| `skip` | 실패한 건전지 건너뛰기 (일시정지 상태에서) |

### `server/line` — 서버 → 화면 (retained, 바뀔 때마다)
```json
{
  "run_id": "20261112-093015-a3f9", "mode": "running", "step": "running", "battery_id": 17,
  "counts": {"A": 9, "B": 4, "NG_VISUAL": 2, "NG_VOLTAGE": 1, "RESORT": 1},
  "on_belt": [17, 18], "agv": {"loaded": 3, "batch": 8, "state": "home"},
  "message": null, "ts": "2026-11-12 09:31:12.300"
}
```
- `counts`: 등급 5개로 나눔 (v1.2)
- `on_belt`: 벨트 위에 있는 퍽의 battery_id (v1.2 추가)
- `mode`: `idle` / `running` / `paused` / `estop` / `manual`
- `battery_id`: 가장 최근에 올린 퍽

### 그 밖에 화면이 구독하는 것
- `server/devices`, `server/events`, `server/results`. 지난 이력은 MySQL 읽기 전용 계정으로 조회
