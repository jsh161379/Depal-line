## 0. 한눈에

```
[서버 PC]
  Mosquitto(브로커) ── 모든 프로그램이 여기에만 접속
  중앙 서버 ─────────── 장치 감시 (하트비트)
  라인 컨트롤러 ─────── 퍽 순서 관리, 계획(PLAN)·보낼 곳 결정, 등급 판정
  YOLO 프로그램 ─────── 팔레트 인식, 검사 부스 결과를 스스로 전송 (vision/result)
  Mega 중계 프로그램 ── cmd/mega ↔ USB 시리얼 ↔ Arduino Mega
  환경 중계 프로그램 ── env_relay.py: sensor/env·event/env ↔ USB 시리얼 ↔ 환경 Uno (v1.5)
  AGV 중계 프로그램 ─── agv_relay.py: cmd/agv ↔ 블루투스 ↔ AGV
  WPF 관리자 프로그램 ─ 현재 상태 표시, 시작/정지 버튼
  DB 저장 프로그램 ──── MySQL 저장
[로봇팔 1: myCobot 280 Pi, 장치 이름 arm1] ── 내장 라즈베리파이가 cmd/arm1을 직접 받음 (팔레트 → 벨트, 퍽째)
[Arduino Mega] ── 서버 PC에 USB. 컨베이어, 측정 헤드, 재분류 서보, 로봇팔 2(MYLOOP+전자석), 도착 센서,
                   비상정지 버튼, 비상정지 부저 (v1.5)
[Arduino Uno (환경, 장치 이름 env)] ── 서버 PC에 USB(시리얼 9600). 가스(MQ-9)·온습도(DHT11) 센서, 환경 경고 부저 (v1.5)
[AGV] ── 블루투스로 AGV 중계와 연결
```
- 팔 1과 Mega는 서로 직접 연결하지 않고, 각자 서버와 따로 연결한다 (하드웨어 확정 11/10). 환경 Uno도 다른 장치와 직접 연결하지 않는다 (v1.5)
- Mega 중계 프로그램, 환경 중계 프로그램, YOLO는 **서버 PC**에서 돈다 (하드웨어 확정 11/10, 11/18)
- 따로 쓰려던 라즈베리파이는 쓰지 않는다 (팀 결정 11/11). 라인의 라즈베리파이는 로봇팔 1 **안에 든 것 하나뿐**이며, 팔 프로그램(MQTT 수신 + 팔 제어)이 이 안에서 돈다 (담당 김초아). 학원 와이파이로 서버 PC(192.168.0.158) 브로커 접속 확인 (11/12)
- "Mega" = Arduino Mega 2560 (핀이 많은 아두이노 보드). "환경 Uno" = 환경 센서·부저만 맡는 Arduino Uno (v1.5)

**기본 원칙**
1. **서버만 명령한다.** 장치끼리 직접 명령하지 않는다.
2. **장치는 자기 일만 한다.** "어디로 보내라"는 서버가, "언제·어떻게 움직이나"는 장치가 정한다. (예: 벨트 속도, 팔 2가 집는 시점은 Mega가 계산)
3. **명령에는 응답이, 장치가 스스로 겪은 일에는 알림이 온다.** v1.2부터 YOLO와 Mega는 명령 없이도 알림(`vision/result`, `event/mega`)을 보낸다. 환경 Uno는 `event/env` (v1.5).
4. **물리 동작은 서버가 자동으로 재시도하지 않는다.** 실패하면 멈추고 작업자가 판단한다.

| 항목 | 규칙 |
|---|---|
| 브로커 | 서버 PC의 Mosquitto, 포트 1883 (홈페이지용 9001 WebSocket은 주문 통신 규약 1장) |
| 메시지 형식 | UTF-8 JSON (메시지 하나 = JSON 한 개) |
| 시각 | 서버 PC 한국 시간 `YYYY-MM-DD HH:MM:SS.mmm` (하트비트의 `ts`만 유닉스 초). Mega·환경 Uno 메시지의 시각은 PC 중계 프로그램이 붙인다 |
| QoS | 하트비트 0, 그 외 전부 1 |
| retained | `status/*`, `server/devices`, `server/line`만 사용 |
| client_id | `server`, `controller`, `arm1`(로봇팔 1, v1.3까지 `pi`), `mega`(Mega 중계), `env`(환경 중계, v1.5), `yolo`, `agv`, `db_saver`. 관리자 프로그램은 `admin-<번호 2자리>` (v1.4, 예: `admin-01`, `admin-02`. 번호는 PC마다 `settings.local.json`의 `AdminNo`에 적음 — PC끼리 겹치면 안 됨. 비우면 `admin-<PC이름>`). 관리자 프로그램 하트비트에는 로그인한 사람 이름 `user`를 싣는다 (로그인 전 null) → 화면에는 "관리자 화면 1 (조시현)"처럼 표시 |
| run_id | 회차 번호. 라인 컨트롤러가 `start` 때마다 새로 만든다 (회차 = 팔레트 한 판) |

## 1-1. 지휘 프로그램 분리 (v0.9.3)

- 순서·판정을 맡는 **라인 컨트롤러(`line_controller.py`, client_id `controller`)**를 중앙 서버(`central_server.py`, 장치 감시·이벤트)와 별도 프로그램으로 둔다.
- 컨트롤러도 `hb/controller` 하트비트와 `status/controller` LWT를 보낸다.
- 컨트롤러는 `server/devices`를 구독해 arm1·mega·yolo가 지연·끊김이 되면 새 퍽을 올리지 않고 일시정지한다. **환경 Uno(`env`)가 끊겨도 라인은 멈추지 않는다** (v1.5).

## 2. 명령과 응답 (cmd / res)

### 명령 형식 — `cmd/<장치>`
```json
{"cmd_id": "7f3a9c1e02b44d8e", "run_id": "20261112-093015-a3f9", "battery_id": 17,
 "action": "pick", "params": {"cell": [0, 2]}, "ts": "2026-11-12 09:31:00.120"}
```

### 응답 형식 — `res/<장치>`
```json
{"cmd_id": "7f3a9c1e02b44d8e", "status": "done", "data": {}, "error": null, "ts": "2026-11-12 09:31:06.874"}
```

| status | 뜻 | 언제 보내나 |
|---|---|---|
| `accepted` | 명령 받음, 시작함 | 받자마자 (1초 안) |
| `done` | 성공적으로 끝남 | 동작이 끝났을 때. 결과값은 `data`에 |
| `failed` | 시도했지만 실패 | `error`에 이유 |
| `rejected` | 시작하지 않음 | 다른 명령 실행 중, 비상정지 상태 등 |

**장치가 지킬 것**
- 같은 `cmd_id`가 다시 오면 다시 실행하지 말고 마지막 응답을 다시 보낸다.
- `estop`은 언제나 즉시 실행한다.

**서버가 지킬 것 (시간 제한, 🟡 임시값)**: accepted까지 2초, done/failed까지는 각 명령 표. 시간 초과 시 라인 일시정지 + ERROR 이벤트

## 3. 장치별 명령

### 3-1. 로봇팔 1 (myCobot 280 Pi) — `cmd/arm1`, `res/arm1` (v1.3까지 `pi`)

| action | params | done의 data | 제한 시간(🟡) | 하는 일 |
|---|---|---|---|---|
| `pick` | `{"cell": [행, 열]}` | `{}` | 20초 | 팔레트 칸에서 **퍽과 건전지를 통째로** 집어 벨트에 올림. 칸은 2줄 × 3칸 (행 0~1, 열 0~2, v1.5.3) |
| `estop` | `{}` | `{}` | 즉시 | 로봇팔 정지 |
| `reset` | `{}` | `{}` | 30초 | 비상정지 해제 후 원점 복귀 |

- 하트비트: `hb/arm1`, 연결 상태 `status/arm1`: `{..., "arm": "ok" / "stopped"}`
- `pick`의 `done` = 퍽이 벨트에 놓임. 서버는 이때 그 `battery_id`를 **벨트 위 퍽 줄**의 맨 뒤에 넣는다.
- 칸이 범위 밖이면 `rejected` (`error`: `bad_cell`). 로봇팔 1 코드 `pi_arm1_v9`·`cam_teach_v5`에 2×3 칸 좌표 반영 (11/21, 김초아)

### 3-1-1. Arduino Mega — `cmd/mega`, `res/mega`, `event/mega`

```
서버 ──MQTT(cmd/mega)──▶ Mega 중계(PC) ──USB 시리얼(JSON 한 줄)──▶ Mega ──▶ 컨베이어, 측정 헤드, ADS1115, 부하 MOSFET,
서버 ◀─MQTT(res/mega, event/mega)── Mega 중계 ◀──USB 시리얼────── Mega       재분류 서보, 로봇팔 2, 도착 센서, 비상정지 버튼·부저
```
- Mega는 MQTT를 쓸 수 없어 USB 시리얼로만 연결한다. PC의 중계 프로그램이 시리얼 ↔ MQTT를 바꾸고 **시각(`ts`)을 붙인다.**
- 중계 ↔ Mega 시리얼은 JSON 한 줄씩 (하드웨어 확정). 세부 키 이름은 하드웨어 담당이 정하고, 중계 프로그램이 이 규약의 MQTT 형식으로 바꾼다.
- 벨트는 **Mega가 직접 켜고 끈다.** 측정 자리 센서에서만 멈출 수 있고, 로봇팔 2가 집을 때는 멈추지 않는다 (측정 자리 출발 후 경과 시간으로 집는 시점을 맞춤).
- 벨트 속도는 Mega가 PWM으로 조절한다: 평소 빠르게, 측정 자리·집는 자리 근처에서만 느리게.
- 걸리는 시간 (🟡 하드웨어 추정 11/10, 실제 구동 후 갱신)
  | 구간 | 시간 | 내역 |
  |---|---|---|
  | 측정 자리 도착 → 측정 끝 | 약 4~5초 | 헤드 내림 1.7초 + 측정 0.4초 + 헤드 올림 1.7초 + 서버 응답 |
  | 측정 자리 출발 → 분류 완료 | 약 12~15초 | 이동 약 6초 + 로봇팔 2 집고 놓기 약 5~8초 |
  | 검사 부스 → 측정 자리 | ❓ | 서버가 PLAN을 이 시간 안에 보내야 함 (서버 처리는 수 ms) |
- 하트비트 `hb/mega`: `{..., "serial": "ok" / "offline", "belt": "run" / "stop", "queue": 2}` (`queue` = Mega가 들고 있는 계획 개수)
  - Mega는 시리얼로 1초마다 하트비트를 보낸다. 끊기면 중계가 `serial: "offline"`으로 바꿔 서버에 알린다 (하드웨어 확정 11/10)
- 센서 (하드웨어 확정 11/10): 퍽 도착 센서 TCRT5000 2개(측정 자리: 정지·시간 기준 / 집는 자리: 실패 감지), 측정 헤드 위쪽 리밋 스위치 1개(헤드가 올라온 것이 확인돼야 벨트 출발). 가스·온습도 센서는 v1.5부터 환경 Uno (3-4)
- 서버 하트비트(`hb/server`)가 3초 이상 끊기면 중계가 Mega에 벨트 정지를 보낸다.
- 실제 Mega + 중계 프로그램으로 라인 연동 시험 통과 (11/13, 로봇팔 1·YOLO는 가짜 장치): 계획·측정·분류 흐름 정상 (재분류 2, B 1)

**명령 (서버 → Mega)**
| action | params | done의 data | 제한 시간(🟡) | 하는 일 |
|---|---|---|---|---|
| `plan` | `{"no": 17, "act": "PASS" / "MEASURE", "to": "NG_VISUAL_BOX" / "RESORT_BOX" / null}` | `{}` | 2초 | 퍽 하나의 계획을 Mega의 계획 줄 맨 뒤에 넣음 |
| `route` | `{"no": 17, "to": "AGV" / "NG_VOLTAGE_BOX" / "RESORT_BOX"}` | `{}` | 2초 | 측정이 끝난 퍽의 보낼 곳. 받으면 벨트 다시 출발. `RESORT_BOX`는 측정에서 거꾸로·접촉 불량·측정 실패일 때 (서보로 쳐냄) |
| `belt` | `{"run": true}` | `{}` | 2초 | 벨트 켜기 (라인 시작·재개) |
| `belt` | `{"run": false}` | `{}` | 2초 | **일시정지**: 그 자리에 멈춤. 측정 중이거나 로봇팔 2가 움직이는 중이면 그 동작만 끝내고 멈춤 |
| `belt` | `{"run": false, "drain": true}` | `{}` (벨트 위 퍽을 모두 분류한 뒤 done) | 60초 🟡 | **종료**: 벨트 위 퍽을 모두 분류한 뒤 멈춤. 그동안 서버는 로봇팔 1에 새 `pick`을 보내지 않음. 서버는 벨트 위 **모든 퍽의 `plan`을 보낸 뒤** drain을 보낸다 (Mega는 계획을 받은 퍽만 알기 때문) |
| `estop` | `{}` | `{}` | 즉시 | 컨베이어 전원 차단, 로봇팔 2 정지, 부하 끔 |
| `reset` | `{}` | `{}` | 30초 | 비상정지 해제 후 원점 복귀, 계획 줄 비움 |

- `plan`의 `act`
  | act | 언제 (서버가 YOLO 결과로 정함) | `to` | 측정 자리에서 |
  |---|---|---|---|
  | `PASS` | 외관 불량 (거꾸로 + 외관 불량 포함) | `NG_VISUAL_BOX` | **멈추지 않고 통과** → 팔 2가 외관불량함에 넣음 |
  | `PASS` | 거꾸로만 (외관 정상, 위 카메라 `plus_up`) | `RESORT_BOX` | **멈추지 않고 통과** → 측정 자리 뒤 서보가 퍽째 쳐냄 |
  | `MEASURE` | 정상 (외관 정상, `minus_up` 또는 `unknown`) | `null` (측정 후 `route`로 정함) | 멈춤 → 측정 → `MEASURED` 알림 → `route` 기다림 |
- Mega는 측정 자리 센서에 퍽이 오면 **계획 줄 맨 앞**을 꺼내 그대로 따른다.
- **계획이 아직 없으면** 벨트를 멈추고 `WAIT_PLAN` 알림을 보낸다. 서버는 YOLO 결과가 없는 것을 확인하고 `plan`(`PASS`, `RESORT_BOX`)으로 답한다 (하드웨어 확정 11/10).
- 서버 응답(`plan`·`route`)이 없으면 Mega는 측정 자리에서 **계속 정지·대기**하고, 10초가 지나면 중계가 `NO_RESPONSE` 알림을 보낸다 (하드웨어 확정). 컨트롤러는 이를 `server/events` WARN으로 바꿔 관리자 화면에 경고를 띄운다. 컨트롤러 자체가 죽은 경우는 중앙 서버의 하트비트 감시가 "controller 끊김"으로 알린다.

**알림 (Mega → 서버) — `event/mega`**
```json
{"ev": "MEASURED", "no": 17, "seq": 42, "data": {"polarity": "normal", "v_open": 1.4429, "v_load": 1.1800,
 "r_load": 3.300, "r_int": 0.735}, "ts": "2026-11-12 09:31:12.300"}
```
| ev | no | data | 언제 |
|---|---|---|---|
| `WAIT_PLAN` | null | `{}` | 측정 자리에 퍽이 왔는데 계획이 없어 벨트를 멈춤 |
| `MEASURED` | 번호 | 측정값 (아래 표) | `MEASURE` 퍽 측정 끝. 벨트는 멈춘 채 `route`를 기다림 |
| `DIVERTED` | 번호 | `{}` | 서보가 퍽째 재분류함으로 쳐냄 |
| `AT_PICK` | 번호 | `{}` | 퍽이 로봇팔 2가 집는 자리에 도착. **센서가 아니라** 측정 자리를 지난 뒤 벨트가 움직인 시간으로 Mega가 계산한 값 |
| `NO_RESPONSE` | 번호 / null | `{"waiting": "plan" / "route"}` | 측정 자리에서 서버 응답을 10초 넘게 기다리는 중 (계속 대기) |
| `SORTED` | 번호 | `{"to": "AGV"}` (실제로 넣은 곳) | 로봇팔 2가 건전지를 함에 넣음 = **배출 완료** |
| `FAULT` | 번호 / null | `{"error": "종류"}` (아래 표) | 장치 이상. 서버는 라인을 일시정지하고 관리자 화면에 표시 |
| ~~`ENV_ALARM`~~ | | | **v1.5부터 환경 Uno가 `event/env`로 보낸다 (3-4).** Mega는 보내지 않는다. 컨트롤러는 옛 방식도 계속 받는다 |

**FAULT 종류** (하드웨어 확정 11/10)
| error | 감지 방법 |
|---|---|
| `SENSOR_TIMEOUT` | 계획은 있는데 측정 자리 센서에 퍽이 올 시간이 지나도 안 옴 |
| `ARM2_FAILED` | 집는 자리 센서: 로봇팔 2가 집은 뒤에도 건전지가 남아 있음 |
| `SERVO_FAILED` | 집는 자리 센서: 재분류로 쳐냈어야 할 퍽이 집는 자리에 옴 |
| `HEAD_FAILED` | 헤드 위쪽 리밋 스위치: 올림 후 안 눌림, 또는 내림 후 안 떨어짐 |
| `ADC_FAILED` | 측정기(ADS1115) 통신 오류 |
- "계획 없이 퍽 도착"은 `WAIT_PLAN`으로 보낸다. 계획과 퍽의 짝이 맞는지는 서버가 `no`와 순서로 판단한다
- 비상정지 버튼은 `FAULT`가 아니라 `event/estop`으로 보낸다 (3-4)
- `seq`: **Mega 자체** 알림 일련번호 (1부터, 재시작 시 1). 서버 건전지 번호와는 별개이며, 서버가 빠진 알림을 찾는 데 쓴다.
- 로봇팔 2는 흐르는 벨트에서 고정 좌표로 집는다. 벨트가 멈추는 곳은 측정 자리 한 곳뿐이다.
- `no`는 Mega가 계획에서 받은 번호를 그대로 돌려준다. 서버는 이 번호로 퍽 줄 순서가 맞는지 확인하고, 다르면 라인을 일시정지한다.

**측정값 (`MEASURED`의 data)** — 극성 판단·내부저항 계산은 Mega가 한다
| polarity | 조건(🟡) | 부하 측정 | v_open | v_load, r_int, r_load |
|---|---|---|---|---|
| `normal` | v_open ≥ 0.1V | 함 | 숫자 | 숫자 |
| `reversed` | v_open < −0.1V (+극이 위) | **안 함** | **null** | null |
| `abnormal` | −0.1V ~ 0.1V (접촉 불량 등) | **안 함** | 숫자(0 근처) | null |
- v1.2 변경: 하드웨어 쪽에서 입력 보호 다이오드를 다시 추가하므로(11/10), 거꾸로일 때 측정값이 약 −0.25V에서 잘린다. 값이 의미 없으므로 v1.0처럼 `reversed`면 `v_open`을 null로 보낸다 (극성 판단에는 충분)
- 측정 회로: ADS1115 A0−A1 차동, 측정 헤드는 전기 실린더 + 포고핀. 무부하 약 0.5초, 부하 0.3~0.4초
- 접촉 불량(`abnormal`)·측정 실패는 Mega가 **한 번 다시 측정**하고, 그래도 같으면 보고한다 (하드웨어 확정 11/10)
- 측정 실패: `MEASURED`의 data에 `{"polarity": null, "error": "ADC_FAILED"}`. **부하 MOSFET은 실패해도 반드시 끈 뒤 알림.**
- 측정 후 재분류(거꾸로·접촉 불량·측정 실패)는 서버가 `route`로 `RESORT_BOX`를 보내고, Mega가 측정 자리 다음의 서보로 퍽째 쳐낸다 (하드웨어 확정 11/10)
- ⚠ 하드웨어 안전 확인: 거꾸로 닿았을 때 IRLZ44N 내부 다이오드를 통한 전류

### 3-2. YOLO — `cmd/yolo`, `res/yolo`, `vision/result`

| action | params | done의 data | 제한 시간(🟡) |
|---|---|---|---|
| `scan_pallet` | `{}` | `{"cells": [[0,0],[0,1],[1,3]], "conf": [0.97,0.95,0.91]}` | 5초 |

- `cells`: 건전지가 **있는** 칸만, [행, 열]. 팔레트 한 판 6개 = **2줄 × 3칸** (행 0~1, 열 0~2, 왼쪽 위가 [0,0]) — 11/21 변경 (v1.5.2까지 2×4, v1.5까지 2×5)
- DB `pallet_slot` = 행 × 3 + 열 + 1 (1~6, 행 우선). 예: [0,2] → 3, [1,0] → 4. 이미 저장된 기록은 그때 식 그대로 (11/20~11/21 행×4, 그 전 행×5)
- ❓ 팔레트 칸을 집는 순서 (시험 후 결정)
- 실행 프로그램: `yolo_vision.py` (이미 있음). 학습은 YOLO11n 학습 도구(라벨 → 학습 → `best.pt`)로 하고, 모델 파일만 바꿔 끼운다
- 학습 사진 (팀 합의 11/12): 위·측면 카메라를 박스에 함께 설치해 동시에 찍어서 YOLO 쪽에 준다. 건전지는 한 종류만 쓴다
- 학습 클래스 (11/19 확정, 팀 라벨링 `classes.txt`). **라벨을 그리기 시작했으므로 클래스 순서·이름을 바꾸지 않는다**
  | 모델 | 클래스 (순서대로) | 박스 |
  |---|---|---|
  | 앞·뒤 (`side_best.pt`, 두 카메라 공용) | 0 `object`, 1 `scratch`, 2 `damage`, 3 `corrosion` | 몸통 `object` 1개 (극 방향 구분 없음) + 불량 부위마다 1개 |
  | 위 (`top_best.pt`) | `minus_up`, `plus_up` | 위에서 보이는 윗면 1개 |
  - 앞·뒤는 극 방향을 구분하지 않는다 → 극 방향은 위 카메라, 애매하면 `unknown` → 측정 자리에서 다시 확인 (팀 결정 11/19)
  - 불량 클래스 이름이 그대로 `defects[].type`이 된다. 몸통(`object`)은 불량이 아니다
  - 파일 이름이 `sticker_`로 시작하는 학습 사진은 박스 없는 음성 샘플(배경·다른 건전지)이다

**검사 부스 결과 — `vision/result` (명령 없이 YOLO가 스스로 전송, YOLO 담당 결정 11/10)**
```json
{"seq": 42, "status": "ok", "result": "defect", "conf": 0.91, "polarity": "minus_up",
 "defects": [{"type": "scratch", "conf": 0.91, "cam": "front"}],
 "sides": [{"cam": "front", "result": "defect", "conf": 0.91, "polarity": "minus_up"}],
 "ts": "2026-11-12 09:31:08.120"}
```
| 필드 | 설명 |
|---|---|
| `seq` | YOLO가 매기는 결과 일련번호 (1부터, 재시작 시 1) |
| `status` | `ok` / `failed` (카메라 오류·신뢰도 미달 → `error`에 이유) |
| `result`, `conf` | 앞·뒤 카메라를 합친 외관 판정: `normal` / `defect` |
| `defects` | 불량 종류 목록 `[{"type", "conf", "cam"}]`. 정상이면 `[]`. 종류가 늘어도 형식은 그대로 (하드웨어 제안 11/10) |
| `polarity` | 세 카메라를 합친 극 방향 `minus_up` / `plus_up` / `unknown` |
| `sides` | (선택) 카메라별 원래 결과. `cam`: `front` / `back` / `top` |

- 카메라 3대 (부스 안 고정): **앞·뒤 = 외관 + 극 방향, 위 = 극 방향**
- 보내는 시점: 퍽이 앞 카메라 화면의 기준선을 지날 때 세 카메라로 판정해 **퍽 하나당 1건**. 앞 모델이 아직 없으면 위 카메라로 기준선을 본다 (`TRIGGER_FALLBACK`). 카메라마다 3장 찍어 판정
- 외관 합치기: 한 대라도 불량이면 불량(두 대 모두 불량이면 신뢰도 높은 쪽), 둘 다 정상이면 정상(conf는 낮은 값)
- 극 방향 합치기: **위 카메라가 신뢰도 기준 이상이면 위 카메라 값 → 아니면 앞·뒤가 같은 값일 때만 채택 → 그 외 `unknown`**
- 중복 방지: 화면 속 건전지 **몸통 박스**를 이전 화면과 위치로 짝지어 기준선 통과를 한 번만 센다 (불량 박스는 세지 않음 — 한 퍽이 두 번 세지지 않게). 벨트 속도로 계산한 최소 간격(`MIN_GAP_SEC`) 안의 두 번째 통과는 버림
- 실패 이유 `error`: `camera_error`(카메라 한 대라도 화면이 안 옴), `low_confidence`(앞·뒤에서 건전지를 못 찾음). 어느 카메라인지 `cams` 목록을 같이 보냄 (서버는 쓰지 않음). 위 카메라 신뢰도 미달은 실패가 아니라 앞·뒤 값 → `unknown`
- `sides`의 위(`top`) 카메라는 극 방향만 보므로 `result`가 null
- 모델이 아직 없는 카메라 (실제 모드): 위 = 판정 없음(앞·뒤 값으로), 앞·뒤 = 정상·방향 모름. 무작위 가짜 판정은 `--fake` 시험 때만 (11/19 수정: 실제 건전지가 불량으로 잘못 가지 않게)
- 불량 종류(`defects[].type`): `scratch`(긁힘), `damage`(손상), `corrosion`(부식) (11/19 확정, v1.5까지의 제안 `dent`·`sticker`는 쓰지 않음). 그 밖은 YOLO 학습 클래스 이름 그대로 (영문 소문자, 64자 이하, 프로그램이 자동으로 맞춤). DB `visual_defects`가 건전지 하나에 여러 행을 받을 수 있어 종류별로 저장 가능
- 서버는 결과를 **벨트 위 퍽 줄에서 아직 YOLO 결과가 없는 가장 앞 퍽**에 붙인다. 붙일 퍽이 없는데 결과가 오면(중복·유령) 버리고 WARN 이벤트를 남긴다.
- 🟡 신뢰도 기준, 기준선 위치, 최소 간격은 실물 시험 후 정함

### 3-4. 비상정지 버튼·환경 센서·부저 (v1.5: 환경 센서·부저를 Uno로 분리)

| 장치 | 연결 | 토픽 | 방향 |
|---|---|---|---|
| 비상정지 버튼 | Mega (중계 뒤 시리얼) | `event/estop` | 중계 → 컨트롤러·DB·관리자 프로그램 |
| 비상정지 부저 | **Mega** (v1.5) | 없음 (Mega가 스스로 울림) | — |
| 가스·온도·습도 센서 | **환경 Uno** (환경 중계 `env_relay.py` 뒤 시리얼) | `sensor/env` | 중계 → DB·관리자 프로그램 |
| 환경 경고 | **환경 Uno** | `event/env` `ENV_ALARM` | 중계 → 컨트롤러 (WARN 이벤트) |
| 환경 경고 부저 | **환경 Uno** | 없음 (Uno가 스스로 울림) | — |

**비상정지 (Mega)**
- 버튼이 눌리면 Mega가 벨트·로봇팔 2를 즉시 멈추고 **비상정지 부저를 울린다**(길게 계속, 버튼 복귀 시 멈춤 🟡). 그 뒤 서버에 알린다. MQTT 메시지는 정지 후 알림이다.
- 부저를 Mega에 따로 두는 이유 (11/18 결정, 부저 2개): 버튼과 부저가 같은 보드에 있어야 서버·와이파이·환경 Uno 상태와 관계없이 울린다.
- ⚠ 하드웨어 확인: 가능하면 모터 12V 전원도 버튼으로 직접 차단 (Mega 코드와 관계없이 멈추도록)
- 컨트롤러는 `BUTTON_PRESSED`를 받으면 회차를 멈추고 `cmd/arm1 estop`, `cmd/mega estop`을 보낸 뒤 `STOP_CONFIRMED`를 발행한다. 버튼이 눌린 동안 `reset` 거부.
- 비상정지 메시지의 `device`는 `mega`. 메시지 형식과 DB 대응: 메시지_형식 4~5장

**환경 센서·부저 (환경 Uno, 장치 이름 `env`, 11/18 하드웨어 결정)**
- 라인 Mega와 따로 둔 Arduino Uno. 서버 PC에 USB로 꽂고, PC의 **환경 중계 `env_relay.py`**(client_id `env`)가 시리얼 ↔ MQTT를 바꾼다. 시각(`ts`)과 회차 번호(`run_id`, `server/line`에서 가져옴)는 중계가 붙인다
- 시리얼 9600, JSON 한 줄씩 (Uno 코드: `server/tools/env_uno/env_uno.ino`)
  | Uno → 중계 | 뜻 | 중계 → MQTT |
  |---|---|---|
  | `{"t":"env","gas":182,"temp":24.1,"hum":41.0}` | 5초 🟡마다 측정값. 온습도 읽기 실패면 `temp`·`hum`이 null | `sensor/env` (`device: "env"`). 온습도 실패면 가스 값만 |
  | `{"t":"alarm","sensor":"gas_1","metric":"GAS","value":612}` | 기준을 넘는 순간 한 번 | `event/env` `ENV_ALARM` |
  | `{"t":"hb"}` | 1초마다 | 중계가 3초 넘게 아무 줄도 못 받으면 `hb/env`의 `serial: "offline"` |
- 하트비트 `hb/env`: `{..., "serial": "ok" / "offline"}`, 연결 상태 `status/env`(LWT). 중앙 서버가 다른 장치와 같이 감시한다 (`EXPECTED_DEVICES`에 `env`)
- **환경 Uno가 끊겨도 라인은 멈추지 않는다** (컨트롤러가 일시정지하는 장치는 arm1·mega·yolo뿐). 관리자 화면 장치 카드에 지연·끊김으로 보인다
- 중계는 시리얼이 끊기면 3초마다 다시 연다 (USB를 뽑았다 꽂아도 됨). `--fake`로 Uno 없이 가짜 값 발행 (실행기가 가짜 장치를 켤 때 사용, 실제 Uno는 `run_all.py --env-port COM번호`)
- `event/env` 형식 (`event/mega`와 같은 모양, `seq`는 중계 자체 번호):
```json
{"ev": "ENV_ALARM", "no": null, "seq": 3, "data": {"sensor": "gas_1", "metric": "GAS", "value": 612}, "ts": "2026-11-18 15:20:14.371"}
```
- `metric`: `GAS` / `TEMPERATURE` / `HUMIDITY` — 같은 센서(`temp_hum_1`)의 온도·습도 경고를 구분. 측정 종류마다 따로, **기준을 넘는 순간 한 번** 보낸다 (해제 기준 아래로 내려간 뒤 다시 넘으면 또 보냄)
- 가스 센서 MQ-9: Uno A0 원시값, `sensor: "gas_1"`, `unit: "raw"`. 온습도 DHT11: D4, `temp_hum_1`, `C` / `%`. 환경 경고 부저: D8. 센서는 더 늘어날 수 있음 (형식 그대로, `sensor` 이름만 추가)
- ⚠ 부저는 경고가 이어지는 동안 반복해서 울리고, 해제 기준 아래로 내려가면 멈춘다. Uno 코드는 `delay()`로 오래 멈추지 않게 짠다 (DHT11을 다시 읽느라 기다리는 동안에도 부저·하트비트 처리). DHT11은 실패 직후 0.3°C·0% 같은 값이 숫자로 나오므로 범위 검사 (습도 1~100%, 온도 1~60°C 밖이면 실패, 실패하면 온습도만 빼고 가스 값은 계속 보냄) — 11/12 실물 시험 반영
- ⚠ MQ-9 히터(약 150mA) 때문에 아두이노 5V가 4.70V까지 떨어져 DHT11이 안 읽힘 → 센서용 별도 5V(GND 공통) (11/12)
- 부저 담당 조시현: 환경 경고 부저(Uno) 시험 완료 (11/12, D8, 경고 중 반복). 비상정지 부저(Mega)는 Mega 코드 담당과 같이 시험
- 경고 기준 🟡 (Uno 코드 맨 위 상수): 가스 200raw(해제 160), 온도 35°C(33), 습도 80%(75). 가스 참고값 (11/12): 깨끗한 공기 약 75~80raw, 라이터 가스 컵 시험 최대 약 300raw
- v1.4까지의 방식(센서·`ENV_ALARM`이 Mega·`event/mega`)도 컨트롤러가 계속 받는다. DB에 이미 저장된 환경 값의 장치 이름은 그대로(`mega`)

## 4. 건전지 처리 흐름 (서버가 퍽 줄로 관리)

```
서버(컨트롤러)                 팔 1(arm1)        YOLO                 Mega
 │ belt {run: true} (회차 시작 때 한 번) ─────────────────────────▶ │
 │ scan_pallet ─────────────────────────────▶ │
 │ battery_id 부여, pick {cell} ──▶ │ 퍽째 벨트에 올림
 │ ◀──────────── done ─────────────│  → 퍽 줄 맨 뒤에 추가
 │                                  (벨트가 흘러 검사 부스 통과)
 │ ◀──────────────── vision/result ─────────│  → 줄에서 결과 없는 첫 퍽에 붙임
 │ 계획 결정 ─── plan {no, act, to} ─────────────────────────────▶ │ 계획 줄에 추가
 │                                                                 │ 측정 자리 센서
 │                                                                 │  PASS: 통과
 │                                                                 │  MEASURE: 정지 → 측정
 │ ◀──────────────────────────────── event/mega MEASURED ──────────│
 │ 등급 판정 ── route {no, to} ──────────────────────────────────▶ │ 벨트 다시 출발
 │ ◀──────────────────── event/mega DIVERTED / AT_PICK / SORTED ───│
 │ server/results 발행 → DB 저장 (SORTED·DIVERTED = 배출 완료)
```
- 여러 퍽이 동시에 벨트 위에 있을 수 있다. 서버는 퍽 줄(battery_id 순서)로 각 퍽의 단계를 따로 관리한다.
- 새 퍽 올리기(`pick`)는 벨트 위 퍽 수가 `MAX_ON_BELT`(🟡) 미만일 때만 한다.
- 계획이 없어 `WAIT_PLAN`이 오면: 줄 맨 앞 퍽에 YOLO 결과가 없으면 `vision.status = failed`로 기록하고 `plan`(`PASS`, `RESORT_BOX`)을 보낸다.

**판정 (서버) — 위에서부터 차례로. 판정 순서는 팀 확정, 전압·내부저항 기준값은 🟡 임시값 (v1.5.2, 11/20 팀 결정 ⑩)**
| 순서 | 조건 | 등급 | dest | 측정 | 옮기는 방법 |
|---|---|---|---|---|---|
| 1 | YOLO 결과 없음·검사 실패 | RESORT | `RESORT_BOX` | 안 함 | 서보 |
| 2 | 외관 불량 (거꾸로 포함) | **NG_VISUAL** | `NG_VISUAL_BOX` (외관불량함) | 안 함 | 팔 2 |
| 3 | 거꾸로 (`plus_up`, 외관 정상) | RESORT | `RESORT_BOX` (재분류함) | 안 함 | 서보 |
| 4 | 측정 결과 reversed / abnormal / 측정 실패 | RESORT | `RESORT_BOX` | 함 | 서보 |
| 5 | 무부하 < 1.50V 🟡 (**개방전압 먼저** — 내부저항과 관계없이) | **NG_VOLTAGE** (전압 낮음) | `NG_VOLTAGE_BOX` (전압불량함) | 함 | 팔 2 |
| 6 | 무부하 ≥ 1.50V, 내부저항 ≤ 1.2Ω 🟡 | A | `AGV` (A 적재 자리) | 함 | 팔 2 |
| 7 | 무부하 ≥ 1.50V, 내부저항 > 1.2Ω | **NG_VOLTAGE** (내부저항 큼) | `NG_VOLTAGE_BOX` | 함 | 팔 2 |

- 현재 등급은 `A`, `NG_VISUAL`(외관이상), `NG_VOLTAGE`(전압이상), `RESORT`(재분류)다. 과거 `B`와 `NG`는 이력용이다.
- 현재 기준 버전은 `temp-2026-11-25-no-b`다. 측정 헤드 실측 후 임시 기준을 조정할 경우 `rule_version`도 변경한다.

**판정 기준값 발행 — `server/rules` (v1.5.2, retained, QoS 1)**
- 컨트롤러가 브로커에 연결될 때와 회차를 시작할 때 발행. DB 저장 프로그램이 `grading_rules`(`rule_version` 고유, `voltage_and_resistance_thresholds` JSON, `effective_at`)에 저장한다. **DB 쓰기는 저장 프로그램만** (11/20 ⑤)
- 검사 성적서(주문 관리 F6)는 연결 회차 결과의 `rule_version`(`battery_cycles.rule_id`)으로 그 회차 기준값을 읽어 합격 기준으로 쓴다 (성적서 합격 기준 = 라인 A 기준, ⑩)
```json
{"rule_version": "temp-2026-11-25-no-b", "effective_at": "2026-11-25 00:00:00.000",
 "thresholds": {"A": {"v_open_min": 1.50, "r_int_max": 1.2}, "order": "v_open_first"},
 "ts": "2026-11-25 09:53:25.041"}
```
- 같은 `rule_version`의 값은 바꾸지 않는다 (다른 값이 오면 저장 프로그램이 경고만 남김). 자세한 칸은 메시지_형식 v1.4.4 5-1
- `unknown`(극 방향 애매)은 측정으로 보낸다. 거꾸로면 측정 자리에서 걸러진다 (2중 확인)

**실패하면**
| 실패 | 서버 동작 |
|---|---|
| pick 실패 | 새 퍽 올리기 멈춤, ERROR 이벤트. 작업자가 "재개/건너뛰기" 선택 |
| YOLO 결과 없음 | `WAIT_PLAN`에 RESORT 계획으로 답함 (위 1번) |
| 측정 실패 | 측정 실패 → RESORT |
| `no`가 퍽 줄 순서와 다름 | 라인 일시정지, ERROR 이벤트 (작업자가 벨트 위 퍽 정리) |
| `FAULT` (ARM2_FAILED·SERVO_FAILED) | 그 퍽은 dest = null, reason에 `배출 실패(<오류>)`를 붙여 결과 저장, 라인 일시정지 |
| `FAULT` (그 밖) | ERROR 이벤트, 라인 일시정지 |
| `ENV_ALARM` (`event/env`) | WARN 이벤트 (라인은 계속) |
| 환경 Uno 끊김 (`hb/env`) | 장치 상태 끊김 표시만 (라인은 계속, v1.5) |
| `NO_RESPONSE` 알림 | WARN 이벤트 (관리자 화면 경고), 라인 일시정지 (새 퍽 안 올림, `belt run:false`). 원인 확인 후 작업자가 재개 |
| 명령 응답 시간 초과 (`plan`·`route` 2초 등, 2장 표) | ERROR 이벤트, 라인 일시정지 |
| 배출 완료 지연 (🟡 퍽을 올린 뒤 60초 안에 `SORTED`·`DIVERTED`가 없음) | ERROR 이벤트, 라인 일시정지 |
| 비상정지 | 벨트 위 퍽은 결과 없이 정리 (작업자가 회수), WARN 이벤트로 번호 기록 |
| 장치 끊김 (arm1·mega·yolo 하트비트) | 라인 일시정지 |

## 5. 작업자 화면 (WPF) ↔ 서버

### `ui/cmd` — 화면 → 서버 (버튼)
| action | 뜻 |
|---|---|
| `start` | 라인 시작 (벨트 켜기, 퍽 올리기 시작) |
| `pause` / `resume` | 일시정지 / 재개 (`belt run:false` → 그 자리 정지, 새 퍽 안 올림) |
| `stop` | 회차 종료 (새 퍽 안 올림 → `belt run:false, drain:true`로 벨트 위 퍽을 모두 분류한 뒤 종료) |
| `estop` | 비상정지 (즉시 `cmd/arm1`, `cmd/mega` estop 전달) |
| `reset` | 비상정지 해제 |
| `skip` | 실패한 건전지 건너뛰기 (일시정지 상태에서) |

### `server/line` — 서버 → 화면 (retained, 바뀔 때마다)
```json
{
  "run_id": "20261112-093015-a3f9", "mode": "running", "step": "running", "battery_id": 17,
  "counts": {"A": 9, "NG_VISUAL": 2, "NG_VOLTAGE": 5, "RESORT": 1},
  "on_belt": [17, 18], "stations": {"measure": [18], "sort": [17]},
  "agv": {"loaded": 3, "batch": 6, "state": "home"},
  "message": null, "ts": "2026-11-12 09:31:12.300"
}
```
- `counts`: 현재 등급 4개의 개수
- `on_belt`: 벨트 위에 있는 퍽의 battery_id (v1.2 추가)
- `stations`: 벨트 위 퍽이 지금 있는 공정 → battery_id 목록 (v1.4.1 추가, 퍽이 없는 공정은 키 없음). 라인 현황 공정 흐름도용
  | 키 | 조건 (컨트롤러가 판단) |
  |---|---|
  | `inspect` | YOLO 결과가 아직 없음 (검사 부스로 가는 중·촬영 중) |
  | `measure` | 측정할 퍽인데 측정값이 아직 없음 (측정 자리로 가는 중·측정 중) |
  | `sort` | 그 밖: 통과 계획을 받았거나, 측정 끝나고 보낼 곳을 받음 (분류로 가는 중) |
  - 공정 흐름도는 `step`(`scan`·`pick`)과 `stations`를 함께 보고 칸을 켠다. `step`은 v1.2부터 라인 전체 상태라 `inspect`·`measure`·`sort` 값은 오지 않는다
  - 발행 시점: 퍽을 올림, 계획 보냄(YOLO 결과·WAIT_PLAN), 측정값 받음, 배출 완료 — 그 밖의 상태 변화 때도
  - 관리자 프로그램: `LineStatus.Stations`로 읽음, 가짜 데이터(FakeLineClient)도 같은 형식. 라인 현황 화면(ProcessViewModel)이 `step` + `stations`로 칸을 켜는지 실제 서버로 확인 필요
- `mode`: `idle` / `running` / `paused` / `estop` / `manual`
- `battery_id`: 가장 최근에 올린 퍽

### 그 밖에 화면이 구독하는 것
- `server/devices`, `server/events`, `server/results`, `sensor/env`, `event/estop`. 지난 이력은 MySQL 읽기 전용 계정으로 조회

### 5-1. 채팅 — `chat/messages` (v1.3, 관리자 프로그램끼리)

- 같은 브로커에 붙은 **관리자 프로그램끼리** 쓰는 단톡방 하나. 서버·장치·DB는 구독하지 않는다. 주문 관리 프로그램도 같은 방에 붙는다 (주문 통신 규약 5장, `ref_kind: "order"`)
- 1:1 대화방은 없다. 대신 `@이름`으로 사람을 부르면 그 사람 화면에서 강조된다 (팀 결정 11/11).
- 관리자 프로그램은 라인 연결과 **따로** 채팅 연결을 만든다: client_id = 관리자 프로그램 client_id + `-chat` (예: `admin-01-chat`). 채팅에 문제가 생겨도 라인 감시·명령은 영향 없음.
- QoS 1, retained 안 씀. 내가 보낸 메시지도 구독으로 한 번 돌아온다 (화면은 이걸 받아 표시).

```json
{"msg_id": "3ea1d8a266364241aa5e1b8a34f94dcb", "from_id": "jsh", "from_name": "조시현", "station": "DEPAL-01",
 "text": "@장성찬 재분류함 비워 주세요", "ref_kind": "alarm", "ref_text": "[주의] Mega 재분류함 가득 참",
 "mentions": [{"id": "jsc", "name": "장성찬"}], "ts": "2026-11-12 09:31:12.300"}
```
| 필드 | 설명 |
|---|---|
| `msg_id` | 메시지 고유 번호 (32자 16진수). 받는 쪽은 같은 번호를 두 번 표시하지 않는다 (QoS 1 중복) |
| `from_id`, `from_name` | 보낸 계정 아이디·이름 |
| `station` | 보낸 프로그램의 라인 이름 (settings의 `StationName`). 같은 사람이 PC 두 대에 있을 때 구분 |
| `text` | 내용 (500자 이하) |
| `ref_kind`, `ref_text` | 붙여 보낸 것: `alarm` / `battery` / `order`(주문 관리) / null, 그 내용 글자 |
| `mentions` | `@`로 부른 사람 `[{"id", "name"}]`. 비어 있으면 그냥 단톡방 메시지. 아이디를 모르면 `id`는 `""` |
| `ts` | 보낸 시각 |

- **나를 부름 판단:** `mentions`에 내 아이디가 있거나 이름이 같으면 "나를 부른 메시지"로 본다 (내가 보낸 글은 제외). 계정이 PC마다 따로 저장돼 아이디가 다를 수 있어서 이름도 같이 본다.
- 나를 부른 메시지는 호박색으로 강조하고 알림 소리를 낸다. 다른 탭을 보던 중이면 채팅 탭을 열 때 "자리를 비운 사이 나를 부른 메시지 N건"을 띄운다.
- 저장: 각 PC의 `data/chat/날짜.jsonl` (지난 7일 불러오기용). DB에는 저장하지 않는다.
- ⚠ 비밀 대화가 아니다: 1883 포트는 계정 없이 열려 있어 누구나 `chat/messages`를 볼 수 있다. 운영에서는 Mosquitto 계정·권한(ACL) 설정이 필요하다.
- ❓ 1:1 대화방·DB 저장은 계정 저장 위치(DB `users` 표)가 정해진 뒤 검토 (7장)
